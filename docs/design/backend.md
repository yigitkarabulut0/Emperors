## 0. The three decisions that shape everything else

1. **Latency budget is dominated by DB round trips.** Neon is in London (eu-west-2). Hetzner has no London region; Falkenstein→London is ~15–18 ms RTT. **DigitalOcean LON1 is ~1–2 ms to Neon eu-west-2.** A 5-round-trip request costs 90 ms from Hetzner and 10 ms from DO LON1. **Pick DigitalOcean, `s-2vcpu-4gb`, LON1.** (If the owner insists on Hetzner Falkenstein, move the Neon project to `aws-eu-central-1` Frankfurt first — do not split them.) Every design below still targets **≤ 3 DB round trips per mutating request**, achieved with multi-CTE single statements and `pgx.Batch` pipelining.

2. **The economy is integer-only.** Gold/XP/diamonds are `bigint`. Every multiplier is an integer in **basis points** (10000 = 1.0×). Rounding is always `floor` (integer division). No `float64` ever touches a currency. This makes server, admin simulator, and client-side display prediction bit-identical, and makes the ledger reconcile exactly.

3. **Time-derived state is never written by a sweeper.** Energy and offline tax are stored as `(value, anchor_timestamp, rate)` triples and settled by a single locking SQL function called at the top of every request that touches the player. This is the core of the design and is covered in §5.

### Justification against Go community norms

- **`cmd/` + `internal/`** is the consensus layout and `internal/` is compiler-enforced. We will add `cmd/` binaries later (worker, admin BFF); the boundary must exist now.
- **No `pkg/`.** Nothing here is meant for external import. `pkg/` is cargo cult (the Go team has said so repeatedly).
- **No `models/`, `utils/`, `helpers/`.** Types live with their behaviour. `domain` holds shared structs only because `game` and `service` both need them and `game` must not import `service`.
- **The one load-bearing rule: `internal/game` is pure.** No `context.Context`, no `*pgxpool.Pool`, no `net/http`, no `time.Now()`. Every function is `func(cfg *gameconfig.Bundle, in X) (Y, error)`. This is what makes (a) the economy unit-testable with zero infrastructure, (b) the balance simulator possible, (c) shop/recruit/battle rolls reproducible for audit. Enforce it in CI:
  ```bash
  go list -deps ./internal/game/... | grep -E 'internal/(db|httpx|service|auth)' && exit 1
  ```
- **`internal/service` owns transactions.** Pattern is always: `BeginTx → settle → read → call internal/game → write → ledger → commit`. Handlers are 15 lines: decode, call service, encode.
- **`internal/store` was deliberately omitted.** sqlc's generated `Queries` type already *is* the repository, and adding a hand-rolled interface layer over it buys nothing but indirection for a two-person team. Services take a `sqlcdb.DBTX` so they work against both `*pgxpool.Pool` and `pgx.Tx`.

## 2. HTTP stack

**Pick: `github.com/go-chi/chi/v5 v5.3.2`** (+ `chi/v5/middleware` for RequestID/RealIP/Recoverer).

**Defence.** Go 1.22+ `net/http.ServeMux` genuinely got good — `"POST /v1/collect"` patterns, `{id}` wildcards, precedence rules. I still reject it here for three concrete reasons:

1. **No middleware primitive and no route groups.** This API has four distinct middleware profiles: `/v1/auth/*` (no auth, hard per-IP limit), `/v1/*` (auth + per-player limit + idempotency), `/admin/*` (admin audience + audit + IP allowlist), `/healthz|/metrics` (nothing). With stdlib mux you hand-wrap every handler or build your own `Group` abstraction — i.e. you reimplement chi, badly.
2. **No `RoutePattern()`.** Prometheus labels and per-route rate-limit config must key on the *pattern* (`/v1/kingdoms/{id}/upgrades/{key}/buy`), not the path, or cardinality explodes. chi gives `chi.RouteContext(r.Context()).RoutePattern()`. With stdlib you maintain a parallel `map[string]RouteConfig` that silently drifts from the router.
3. **`Mount()`** lets `/admin` be a fully independent sub-router with its own middleware stack in one line, which is how we keep the admin surface out of the game surface in the same binary.

chi is 100% `net/http` (`func(http.ResponseWriter, *http.Request)`), zero third-party deps in the core, <1000 LOC router. **echo and gin are rejected**: custom handler signatures and custom `Context` types infect every function, make `httptest` awkward, and buy nothing we need. There is no lock-in cost to chi — deleting it later is a mechanical refactor.

### Middleware chain (exact order)

```go
r := chi.NewRouter()
r.Use(middleware.RealIP)                       // trust Caddy's X-Forwarded-For (exactly 1 hop)
r.Use(mw.RequestID)                            // uuid.NewV7() → ctx + X-Request-Id response header
r.Use(mw.Recover(sentryHub))                   // panic → 500 + Sentry with stack + request_id
r.Use(mw.Logger(slogHandler))                  // emits AFTER handler: route, method, status, dur_ms, bytes, player_id
r.Use(mw.Metrics(promRegistry))                // http_requests_total / http_request_duration_seconds by RoutePattern
r.Use(mw.Timeout(10 * time.Second))            // context deadline; handler must respect it
r.Use(mw.MaxBytes(64 << 10))                   // http.MaxBytesReader
r.Use(mw.ClientVersionGate(cfg.MinClientVer))  // 426 Upgrade Required for killed builds
r.Use(mw.IPRateLimit(ipLimiter))               // global per-IP token bucket

r.Group(func(r chi.Router) {                   // public
    r.Get("/healthz", h.Healthz)               // no DB
    r.Get("/readyz", h.Readyz)                 // pings DB; flips to 503 on SIGTERM
    r.Get("/v1/time", h.Time)
    r.Get("/v1/config", h.Config)              // ETag / 304
    r.Post("/v1/auth/device", h.AuthDevice)
    r.Post("/v1/auth/refresh", h.AuthRefresh)
})

r.Group(func(r chi.Router) {                   // game
    r.Use(mw.Auth(verifier))                   // Ed25519 JWT → domain.Actor in ctx
    r.Use(mw.PlayerRateLimit(playerLimiter))   // per (player_id, route) bucket
    r.Use(mw.Idempotency(idemStore))           // only acts on routes tagged mutating
    mountGame(r, h)
})

r.Mount("/admin", adminRouter(h, adminVerifier))
```

`Recover` sits above `Logger` so a panic inside the logger is still caught, and `Logger` sits above `Timeout` so a timed-out request is still logged with its true duration.

### CORS
The Godot client is native — it sends no `Origin` and needs no CORS. CORS (`github.com/rs/cors v1.11.1`) is applied **only on the `/admin` sub-router**, allow-listing the exact Vercel deployment origin. Do not enable it globally.

### Rate limiting
`golang.org/x/time/rate v0.15.0` token buckets held in a `hashicorp/golang-lru/v2 v2.0.7` LRU (100k entries) keyed `player_id|route_pattern`, plus a second LRU keyed by `/24` IP prefix for `/v1/auth/device`. Per-route limits live in the config bundle so they're tunable from the admin panel without a deploy.

| Route | Limit |
|---|---|
| `POST /v1/auth/device` | 5/min per IP /24, 30/hour |
| `POST /v1/auth/refresh` | 20/min per player |
| `GET /v1/state` | 60/min per player |
| `POST /v1/collect` | 60/min per player (energy is the real limiter) |
| `POST /v1/attack` | 30/min per player |
| `GET /v1/shop`, `/v1/attack/targets` | 30/min per player |
| all other mutating | 30/min per player |
| global per IP | 300/min |

Exceeding returns `429` with `Retry-After` and increments `game_rate_limited_total{route}`. A player flagged by the anomaly detector gets `players.throttle_level` > 0, which multiplies their buckets by `1/(1+level)` — **shadow throttling**, so a cheater degrades without learning why.

## 3. Database access

**Pick: `github.com/jackc/pgx/v5 v5.10.0` + `github.com/sqlc-dev/sqlc v1.31.1` (`sql_package: "pgx/v5"`). No ORM.**

**Defence.** The hard parts of this backend are precisely what an ORM hides: multi-CTE data-modifying statements, `SELECT … FOR UPDATE` with explicit lock ordering, `INSERT … ON CONFLICT DO UPDATE … RETURNING`, `unnest($1::int[], $2::int[])` array parameters, PG18 `RETURNING OLD.gold, NEW.gold`. With GORM/bun/ent, 100% of the interesting code becomes `db.Raw(...)` — so you pay the ORM's reflection, N+1 hazards and migration friction for zero benefit. sqlc goes the other way: it parses the real schema with PostgreSQL's own grammar, so a typo'd column or a changed type is a **compile error**, and it emits plain structs with no reflection. ent is genuinely well-engineered but cannot express `app.settle_player` composition and its schema-as-Go-code fights goose.

### sqlc.yaml

```yaml
version: "2"
sql:
  - engine: postgresql
    schema:  "db/migrations"          # goose files double as the schema source
    queries: "db/queries"
    gen:
      go:
        package: "sqlcdb"
        out: "internal/db/sqlcdb"
        sql_package: "pgx/v5"
        emit_pointers_for_null_types: true
        emit_json_tags: false
        emit_empty_slices: true
        emit_result_struct_pointers: false
        overrides:
          - db_type: "timestamptz"
            go_type: "time.Time"
          - db_type: "pg_catalog.numeric"
            go_type: "github.com/jackc/pgx/v5/pgtype.Numeric"
```

**UUID representation.** Go 1.27 ships a stdlib `uuid` package (`uuid.UUID [16]byte`, `New()`, `NewV4()`, `NewV7()`, `Parse`, `MustParse`, `Compare`). Do **not** override sqlc's uuid type to it blindly — pgx's default type map may or may not wrap a named `[16]byte` correctly, and getting that wrong is a runtime scan failure. **Let sqlc generate `pgtype.UUID` in `internal/db/sqlcdb`, and convert at the `internal/service` boundary** with two 6-line helpers (`toPG(uuid.UUID) pgtype.UUID`, `fromPG(pgtype.UUID) uuid.UUID`). It's a 16-byte copy. If, at implementation time, you verify that `m.RegisterDefaultPgType(uuid.UUID{}, "uuid")` in `AfterConnect` round-trips correctly in both binary and text formats, you may switch the override — but ship the safe version first.

IDs themselves are generated **in Postgres** with PG18's built-in `uuidv7()` as a column default. Reasons: time-ordered so B-tree inserts stay at the right edge (no page splits, unlike v4), no extra Go dependency, and the DB is the serialization point anyway.

### Neon pooled endpoint: what it forbids

Neon's pooled host (`…-pooler.eu-west-2.aws.neon.tech`) is **PgBouncer in `pool_mode=transaction`** with `max_client_conn=10000`, `default_pool_size = 0.9 × max_connections`, `query_wait_timeout=120`, and — critically — **`max_prepared_statements=1000`**.

**Forbidden on the pooled endpoint** (a connection is only yours for the duration of a transaction; between transactions you get a different backend):

| Forbidden | Why | What we do instead |
|---|---|---|
| `SET` / `RESET` (session vars) | Lands on a random backend; leaks to other tenants | `SET LOCAL` **inside a transaction** (allowed — transaction-scoped), or a server-side default |
| `LISTEN` / `NOTIFY` | Needs a pinned session | Poll (`config_versions` every 30 s); or use the direct endpoint |
| `pg_advisory_lock` (session-scoped) | You lock on backend A and unlock on backend B → **permanently leaked lock** | `pg_advisory_xact_lock()` — transaction-scoped, fully pgbouncer-safe |
| SQL-level `PREPARE` / `EXECUTE` / `DEALLOCATE` | PgBouncer cannot rewrite them | Protocol-level prepared statements only (pgx does this natively) |
| `WITH HOLD` cursors | Outlive the transaction | Cursor-based pagination with `WHERE (k,id) > ($1,$2)` |
| Temp tables without `ON COMMIT DROP` | Outlive the transaction | `CREATE TEMP TABLE … ON COMMIT DROP` (fine) |
| `LOAD` | — | n/a |
| Long-running transactions | Pin a scarce server connection | `statement_timeout` + `idle_in_transaction_session_timeout` (below) |
| Startup `RuntimeParams` (e.g. `timezone`) | PgBouncer only tracks a whitelist; unlisted params can cause errors or cross-tenant leakage | Set **nothing**. All timestamps are `timestamptz` (absolute) and pgx uses binary format, so session TZ is irrelevant. |

**Prepared statements are NOT forbidden.** Because Neon sets `max_prepared_statements=1000`, PgBouncer ≥1.22 rewrites protocol-level Parse/Bind/Execute onto internal names (`PGBOUNCER_n`) per server connection. This has been verified working with pgx's default `QueryExecModeCacheStatement`. So:

```
default_query_exec_mode=cache_statement     # ← use this; you get server-side plan caching
statement_cache_capacity=256
```

with an **escape hatch**: `DB_QUERY_EXEC_MODE` env var. If you ever see `ERROR: prepared statement "stmtcache_…" does not exist` (SQLSTATE `26000`) in production — meaning Neon changed its PgBouncer config — flip it to `describe_exec` and redeploy in 90 seconds. Also add a startup self-test: run 3 trivial queries on 3 different pooled connections and log a WARN if any fails with 26000.

### Timeouts (the non-obvious part)

You cannot `SET statement_timeout` per session through PgBouncer. Two mechanisms, use **both**:

1. **Server-side defaults**, applied once by a migration, inherited by every backend regardless of pooling:
   ```sql
   ALTER ROLE emperors_app SET statement_timeout = '8s';
   ALTER ROLE emperors_app SET idle_in_transaction_session_timeout = '10s';
   ALTER ROLE emperors_app SET lock_timeout = '3s';
   ```
   `lock_timeout=3s` is the safety net for `FOR UPDATE` pile-ups: a hot row never blocks a request longer than 3 s; the client gets a `55P03 lock_not_available` → mapped to `503 try_again` with `Retry-After: 1`.
2. **`SET LOCAL`** inside a transaction for the rare exception (the anomaly scan, admin bulk ops): `SET LOCAL statement_timeout = '60s';`.

**Direct DSN** (`DATABASE_URL_DIRECT`): same host without `-pooler`, `pool_max_conns=4`, `pool_min_conns=0`. The direct endpoint's ceiling scales with compute size (≈450 on 1 CU); keep our footprint tiny.

Sizing rationale: at 1–2 ms RTT and ~3 ms of server work, one connection sustains ~200 tx/s; 20 connections ≈ 4000 tx/s, an order of magnitude beyond a launch-scale idle game. Alert when `pool.Stat().EmptyAcquireCount()` grows or acquire p99 > 5 ms; raise `pool_max_conns` before anything else.

**Neon operational notes.** Scale-to-zero suspends the compute after 5 minutes idle; a cold start costs a few hundred ms. Live traffic will keep it warm, but **disable scale-to-zero on the production branch** to remove cold-start tail latency, and keep it enabled on the `staging` branch (a copy-on-write clone of prod — Neon branching is the single best reason to be on Neon for this project; use it for every schema change rehearsal and for restore drills). `connect_timeout=10` plus pgx's automatic reconnect covers a resume mid-request.

### Isolation and locking strategy

**READ COMMITTED everywhere (the default), with explicit pessimistic `SELECT … FOR UPDATE` row locks.**

- **Reject SERIALIZABLE.** Our hot rows are single-player rows; SSI would turn self-contention (a player double-tapping *Collect*) into `40001` retry storms with unbounded latency, and would add read-write conflict tracking cost on every query for a benefit we get more cheaply from a row lock.
- **Reject optimistic concurrency (version column + CAS retry loop) for the player row.** The contention is *self*-contention on one row: a lock costs one wait; a CAS loop costs N wasted transactions. Pessimistic is strictly better and has bounded latency thanks to `lock_timeout`.
- **Use optimistic exactly once**, where the object is naturally single-shot: consuming a kingdom invite —
  `UPDATE kingdom_invites SET accepted_at = $2 WHERE id = $1 AND accepted_at IS NULL RETURNING id` → 0 rows means "already used", no lock needed.

Deadlock/serialization retry wrapper (belt and braces — with strict lock ordering we should never hit `40P01`):

```go
// internal/db/tx.go
func (p *Pools) InTx(ctx context.Context, fn func(context.Context, pgx.Tx) error) error {
    const maxAttempts = 3
    for attempt := 0; ; attempt++ {
        err := p.once(ctx, fn)
        var pgErr *pgconn.PgError
        if errors.As(err, &pgErr) &&
            (pgErr.Code == "40001" || pgErr.Code == "40P01") && attempt < maxAttempts-1 {
            metrics.TxRetries.Inc()
            time.Sleep(time.Duration(1<<attempt)*8*time.Millisecond + jitter(5*time.Millisecond))
            continue
        }
        return err
    }
}

func (p *Pools) once(ctx context.Context, fn func(context.Context, pgx.Tx) error) error {
    tx, err := p.RW.BeginTx(ctx, pgx.TxOptions{IsoLevel: pgx.ReadCommitted})
    if err != nil { return err }
    // WithoutCancel so rollback still runs when the client hangs up mid-request.
    defer tx.Rollback(context.WithoutCancel(ctx))
    if err := fn(ctx, tx); err != nil { return err }
    return tx.Commit(ctx)
}
```

Retrying is only safe because the idempotency row (§6) lives inside the same transaction and rolls back with it.

## 4. Migrations

**Pick: `github.com/pressly/goose/v3 v3.28.0`**, run against the **direct** endpoint, embedded via `embed.FS`, driven with Go 1.24+ tool directives.

**Defence.**
- vs **golang-migrate**: goose keeps up+down in one file (half the files, no drift), supports **Go migrations** in the same version sequence (we will need data backfills — e.g. recomputing `players.power` after an items change — that cannot be expressed in SQL alone), has `-- +goose NO TRANSACTION` for `CREATE INDEX CONCURRENTLY`, and exposes a programmatic `goose.Provider` API so `cmd/api` can verify-but-not-apply on boot.
- vs **Atlas**: declarative schema and migration linting are genuinely excellent, but the valuable half is a paid cloud product, it adds a non-Go binary to CI, and a two-person team does not have the schema-review volume to amortise it.

**Locking:** goose's `NewPostgresSessionLocker` uses *session-scoped* advisory locks — which is exactly why migrations run on the **direct** endpoint, never the pooled one.

Enforced by review checklist and by the fact that CD runs the previous image's integration tests against the new schema.

## 5. ★ Lazy time-based resource accrual

This is the heart of the backend. Two resources accrue continuously: **energy** (capped at `energy_max`) and **offline tax gold** (capped at 8 h of production). Neither is ever advanced by a background job.

### 5.1 Representation

Each resource is a triple `(value, anchor, rate)` on the `players` row:

| Column | Type | Meaning |
|---|---|---|
| `energy_current` | `int` | energy at `energy_anchor_at` |
| `energy_max` | `int` | cap (from stat points + family upgrades) |
| `energy_period_ms` | `bigint` | **milliseconds per 1 energy** — a period, not a rate |
| `energy_anchor_at` | `timestamptz` | last exactly-settled instant |
| `tax_pending_micro` | `bigint` | unclaimed tax in **micro-gold** (1e-6 gold) |
| `tax_rate_micro_per_s` | `bigint` | micro-gold per second |
| `tax_cap_seconds` | `int` | 28800 (8 h) |
| `tax_anchor_at` | `timestamptz` | last exactly-settled instant |
| `rate_config_ver` | `int` | config version the two rates were derived from |
| `settled_at` | `timestamptz` | bookkeeping / debugging |

**Why a period (ms per unit) rather than a rate (units per ms):** it makes the arithmetic exact integer division with no floating point and no accumulated drift. `gained = elapsed_ms / period_ms` (integer division), and the anchor advances by exactly `gained * period_ms`, so the sub-tick remainder is preserved perfectly. With a fractional rate you must either carry a fractional remainder column or lose progress on every poll.

**The remainder is the whole game.** Naive implementations set `anchor = now` after crediting. With a 60 s period and a client polling `/v1/state` every 10 s, you'd discard 10 s of progress six times a minute and energy would *never* regenerate. Advancing the anchor only by the consumed amount is what makes polling frequency irrelevant.

### 5.2 The settle function

One PL/pgSQL function, called by **every** code path that reads or mutates a player. It is the only place in the system that moves an anchor.

```sql
-- db/migrations/0002_settle.sql
CREATE SCHEMA IF NOT EXISTS app;

CREATE OR REPLACE FUNCTION app.settle_player(p_id uuid, p_now timestamptz DEFAULT NULL)
RETURNS players
LANGUAGE plpgsql
AS $$
DECLARE
    r          players;
    ts         timestamptz;
    e_period   bigint;
    e_elapsed  bigint;   -- milliseconds
    e_gain     bigint;
    t_elapsed  bigint;   -- whole seconds
    t_gain     bigint;
    t_cap      bigint;
BEGIN
    ts := COALESCE(p_now, now());          -- now() is transaction-start time: stable within the tx

    -- The lock. Everything after this is serialized per player.
    SELECT * INTO r FROM players WHERE id = p_id FOR UPDATE;
    IF NOT FOUND THEN
        RAISE EXCEPTION 'player % not found', p_id USING ERRCODE = 'no_data_found';
    END IF;

    -- Monotonicity guard: a clock that jumps backwards must never rewind an anchor.
    ts := GREATEST(ts, r.energy_anchor_at, r.tax_anchor_at);

    ---------------------------------------------------------------- ENERGY
    e_period  := GREATEST(1, r.energy_period_ms);
    e_elapsed := GREATEST(0, (EXTRACT(EPOCH FROM (ts - r.energy_anchor_at)) * 1000)::bigint);
    e_gain    := LEAST(e_elapsed / e_period,                                   -- integer division
                       GREATEST(0, r.energy_max::bigint - r.energy_current::bigint));

    IF r.energy_current::bigint + e_gain >= r.energy_max::bigint THEN
        r.energy_current   := r.energy_max;
        r.energy_anchor_at := ts;                          -- at cap: bank nothing further
    ELSE
        r.energy_current   := r.energy_current + e_gain::int;
        r.energy_anchor_at := r.energy_anchor_at
                              + ((e_gain * e_period) * interval '1 millisecond');  -- exact
    END IF;

    ---------------------------------------------------------------- TAX
    t_cap     := r.tax_cap_seconds::bigint * r.tax_rate_micro_per_s;
    t_elapsed := GREATEST(0, FLOOR(EXTRACT(EPOCH FROM (ts - r.tax_anchor_at)))::bigint);
    t_gain    := LEAST(t_elapsed * r.tax_rate_micro_per_s,
                       GREATEST(0, t_cap - r.tax_pending_micro));

    r.tax_pending_micro := r.tax_pending_micro + t_gain;
    IF r.tax_pending_micro >= t_cap THEN
        r.tax_anchor_at := ts;                             -- offline cap: excess time is discarded
    ELSE
        r.tax_anchor_at := r.tax_anchor_at + (t_elapsed * interval '1 second');
    END IF;

    UPDATE players p
       SET energy_current    = r.energy_current,
           energy_anchor_at  = r.energy_anchor_at,
           tax_pending_micro = r.tax_pending_micro,
           tax_anchor_at     = r.tax_anchor_at,
           settled_at        = ts
     WHERE p.id = p_id
    RETURNING p.* INTO r;

    RETURN r;
END;
$$;
```

Called from sqlc as a normal query:

```sql
-- db/queries/players.sql
-- name: SettlePlayer :one
SELECT * FROM app.settle_player($1, $2);
```

**Why PL/pgSQL and not Go.** This is the one exception to "logic lives in Go", and it earns it: (a) it must be atomic with the lock it takes, (b) it is called by literally every endpoint, so collapsing SELECT-FOR-UPDATE + UPDATE + RETURNING into **one round trip** saves ~30–40% of the DB time of a typical request, (c) it contains no *balance* data — only mechanism. The balance numbers (`energy_period_ms`, `tax_rate_micro_per_s`) are computed in Go from the config bundle and *stored* on the row; the function just integrates them over time. So the admin panel still controls all balance.

### 5.3 Why concurrent requests cannot double-credit

Three concurrent `POST /v1/collect` from the same player (mobile retry storm):

1. T1 `BEGIN` → `SELECT … FOR UPDATE` acquires the row lock, computes `e_gain` from the **committed** anchor, updates, commits.
2. T2 blocked at `FOR UPDATE`. When T1 commits, Postgres re-evaluates T2's locking read against the **new row version** (EvalPlanQual). T2 therefore reads `energy_anchor_at` as T1 left it, so `e_elapsed ≈ 0` and `e_gain = 0`. No double credit.
3. T3 likewise.

The properties that make this airtight:
- **The read that computes the gain is the same statement that takes the lock.** Never read the player in Go, compute in Go, then write — that is a lost-update by construction under READ COMMITTED.
- **All derived values are computed from `r`, which came from the locking read**, not from any earlier snapshot.
- **The anchor is monotonically non-decreasing**, guarded by `GREATEST`.
- Under `lock_timeout=3s`, a pathological pile-up degrades to `503 try_again` instead of hanging.

The correctness argument is therefore: *settle is idempotent with respect to wall-clock time.* Calling it N times at instant `t` produces the same state as calling it once. That is also why `GET /v1/state` — which writes — needs no idempotency key and is safe to retry blindly.

### 5.4 Rate changes mid-interval

**Universal rule: settle with the OLD rate first (which advances the anchor to an exact tick boundary), then write the NEW rate.** Because settle leaves the anchor at a point in the past that is exactly consistent with the old rate, the interval is cleanly split and no time is double-counted or lost.

The residual subtlety: after settling below cap, `now - energy_anchor_at` is a partial tick of up to `old_period - 1` ms. If we just leave it, that partial progress is now measured against the *new* period, which silently rescales it. Handle it exactly by **carrying the fraction**:

```
fraction   = (now - anchor) / old_period          # 0 ≤ fraction < 1
new_anchor = now - fraction * new_period
```

```sql
CREATE OR REPLACE FUNCTION app.apply_rates(
    p_id uuid,
    p_now timestamptz,
    p_energy_max int,
    p_energy_period_ms bigint,
    p_tax_rate_micro_per_s bigint,
    p_tax_cap_seconds int,
    p_config_ver int
) RETURNS players
LANGUAGE plpgsql AS $$
DECLARE
    r          players;
    ts         timestamptz;
    old_period bigint;
    new_period bigint;
    rem_ms     bigint;
BEGIN
    r  := app.settle_player(p_id, p_now);   -- ← settle with the OLD rates. row is now locked.
    ts := COALESCE(p_now, now());

    old_period := GREATEST(1, r.energy_period_ms);
    new_period := GREATEST(1, p_energy_period_ms);

    rem_ms := GREATEST(0, (EXTRACT(EPOCH FROM (ts - r.energy_anchor_at)) * 1000)::bigint);
    rem_ms := LEAST(rem_ms, old_period - 1);            -- at cap this is 0

    UPDATE players p SET
        energy_max           = p_energy_max,
        energy_current       = LEAST(p.energy_current, p_energy_max),
        energy_period_ms     = new_period,
        energy_anchor_at     = ts - ((rem_ms * new_period / old_period) * interval '1 millisecond'),
        tax_rate_micro_per_s = p_tax_rate_micro_per_s,
        tax_cap_seconds      = p_tax_cap_seconds,
        tax_anchor_at        = ts,                       -- tax settles at 1 s granularity; snap
        rate_config_ver      = p_config_ver
      WHERE p.id = p_id
    RETURNING p.* INTO r;
    RETURN r;
END; $$;
```

Every path that changes a rate goes through `apply_rates`: buying a family upgrade, allocating stat points into Max Energy, joining/leaving a kingdom, an admin adjustment, and **config republication**.

### 5.5 Config publication without a global sweep

A new config bundle can change base regen or base tax for everyone. Do **not** sweep 100k rows. Instead, migrate rates **lazily**, in the service layer, on the player's next request:

```go
// internal/service/common.go
func (s *Service) settleAndSync(ctx context.Context, tx pgx.Tx,
    playerID uuid.UUID, now time.Time) (domain.Player, error) {

    q   := sqlcdb.New(tx)
    cfg := s.cfg.Load()                                   // *gameconfig.Bundle, atomic.Pointer

    row, err := q.SettlePlayer(ctx, toPG(playerID), now)   // OLD rates — correct for the past interval
    if err != nil { return domain.Player{}, err }

    if int(row.RateConfigVer) == cfg.Version {
        return domain.FromRow(row), nil                    // fast path: 1 round trip
    }

    // Slow path, taken exactly once per player per config publish.
    ups, err := q.ListPlayerUpgrades(ctx, row.ID)
    if err != nil { return domain.Player{}, err }
    kd, err := q.GetKingdomForPlayerOrNil(ctx, row.ID)
    if err != nil { return domain.Player{}, err }

    rates := economy.DeriveRates(cfg, domain.FromRow(row), ups, kd)   // PURE
    row, err = q.ApplyRates(ctx, sqlcdb.ApplyRatesParams{
        PID: row.ID, PNow: now,
        PEnergyMax: rates.EnergyMax, PEnergyPeriodMs: rates.EnergyPeriodMs,
        PTaxRateMicroPerS: rates.TaxMicroPerSec, PTaxCapSeconds: rates.TaxCapSeconds,
        PConfigVer: int32(cfg.Version),
    })
    return domain.FromRow(row), err
}
```

Because `apply_rates` internally settles again (a no-op the second time — settle is idempotent), the whole thing is correct even though it spans two statements inside one locked transaction.

### 5.6 The design constraint that removes an entire class of complexity

A **kingdom** upgrade that raised the passive tax rate would change the rate for up to 50 members at once, requiring a settle-storm on purchase. **Recommendation: restrict continuous-rate effects (energy regen period, tax rate, energy cap) to sources the player alone controls — family upgrades and stat points. Make kingdom upgrades affect only discrete-event multipliers: collect gold, XP gain, attack loot %, shop price discount.** Those are read live from the config + kingdom row at award time, so no settle is ever needed.

This is a game-design change, so it is an owner question. If the owner insists kingdom upgrades must boost tax, the fallback is bounded and implementable: on purchase, call `SettlePlayer` + `ApplyRates` for every member **in ascending `player_id` order** using a single `pgx.Batch` (pipelined — one network round trip, guaranteed execution order, consistent with the global lock ordering in §8).

```go
b := &pgx.Batch{}
slices.SortFunc(memberIDs, func(a, c uuid.UUID) int { return a.Compare(c) })  // Go 1.27 stdlib uuid
for _, id := range memberIDs {
    b.Queue(`SELECT * FROM app.apply_rates($1,$2,$3,$4,$5,$6,$7)`, id, now, /*…*/)
}
br := tx.SendBatch(ctx, b)
defer br.Close()
```

## 6. Atomicity and idempotency

### 6.1 The idempotency table

```sql
CREATE TABLE idempotency_keys (
    player_id     uuid        NOT NULL REFERENCES players(id) ON DELETE CASCADE,
    key           text        NOT NULL CHECK (length(key) BETWEEN 16 AND 64),
    endpoint      text        NOT NULL,
    request_hash  bytea       NOT NULL,          -- sha256 of (method|route|canonical body)
    status        smallint    NOT NULL,          -- 0 = in_flight, 1 = complete
    response_code int,
    response_body jsonb,
    created_at    timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (player_id, key)
);
CREATE INDEX idempotency_keys_gc_idx ON idempotency_keys (created_at);
```

### 6.2 The protocol

The client generates one `Idempotency-Key` (a `uuidv7`) **per user intent** — per button tap, not per HTTP attempt — persists it to disk *before* the first send, and reuses it across retries and app restarts. Retries use exponential backoff with jitter: `min(8s, 250ms · 2^n) + rand(0..250ms)`.

Server, all inside **one** transaction:

```
BEGIN
  INSERT INTO idempotency_keys (player_id, key, endpoint, request_hash, status)
  VALUES ($1,$2,$3,$4,0)
  ON CONFLICT (player_id, key) DO NOTHING
  RETURNING key;

  ── returned a row ──────────────────────────────────────────────────────
  │ We own this key. Proceed:
  │   SAVEPOINT action;
  │   ... run the use-case ...
  │   on BUSINESS error (insufficient gold, shielded target, level gate):
  │       ROLLBACK TO SAVEPOINT action;          ← keeps the idempotency row alive
  │   UPDATE idempotency_keys SET status=1, response_code=$c, response_body=$b
  │    WHERE player_id=$1 AND key=$2;
  │ COMMIT                                        ← state change + stored response are atomic
  │
  ── returned nothing ────────────────────────────────────────────────────
  │ SELECT * FROM idempotency_keys
  │  WHERE player_id=$1 AND key=$2 FOR UPDATE NOWAIT;
  │   • 55P03 (locked)  → 409 request_in_flight, Retry-After: 1
  │   • status = 0      → 409 request_in_flight, Retry-After: 1
  │   • hash mismatch   → 422 idempotency_key_reuse
  │   • status = 1      → replay stored response, header Idempotent-Replay: true
  └───────────────────────────────────────────────────────────────────────
```

Three properties worth stating explicitly:

- **Insert-first, not select-then-insert.** The naive check-then-act is a race even under READ COMMITTED: two workers both see "absent", both insert, one loses on the PK — but the loser may already have executed side effects. `ON CONFLICT DO NOTHING RETURNING` collapses claim and detect into one atomic step.
- **`FOR UPDATE NOWAIT`, not a blocking wait.** A blocking wait would hold a mobile retry hostage for up to `statement_timeout`. Fail fast with `409` and let the client's backoff do the work (this is Stripe's behaviour).
- **Business failures are committed; infrastructure failures are rolled back.** A `402 insufficient_gold` is stored, so the retry gets the identical answer. A deadlock or dropped connection rolls the whole transaction back including the key, so the retry starts clean — which is exactly what makes the `InTx` retry wrapper safe.

GC: the scheduler deletes rows older than 48 h nightly (`DELETE … WHERE created_at < now() - interval '48 hours'`, batched at 10k rows).

### 6.3 Which routes require a key

**Required (middleware rejects with `400 idempotency_key_required` if absent):** `POST /v1/collect`, `/v1/tax/claim`, `/v1/shop/buy`, `/v1/shop/reroll`, `/v1/soldiers/slots/buy`, `/v1/soldiers/recruit`, `/v1/soldiers/{id}/dismiss`, `/v1/attack`, `/v1/inventory/sell`, `/v1/family/upgrades/{key}/buy`, `/v1/player/stats/allocate`, `/v1/player/equip`, `/v1/player/unequip`, `/v1/player/name`, all `/v1/kingdoms/*` mutations, `/v1/iap/apple/verify`.

**Not required:** every `GET`; `POST /v1/auth/device` (naturally idempotent — keyed on `sha256(device_secret)`); `POST /v1/auth/refresh` (rotation has its own reuse-detection semantics); `POST /v1/notifications/read` (set semantics).

### 6.4 The atomic collect — exact SQL

The whole action in **one statement**: settle, guard, bump the per-job counter, apply milestone + global multipliers, spend energy, award gold/XP, recompute level, write the ledger. Balance data enters as array parameters so it stays owned by the config bundle, not by SQL.

```sql
-- db/queries/collect.sql
-- name: Collect :one
WITH settled AS (
    SELECT * FROM app.settle_player(@player_id, @now)
),
guard AS (
    -- Empty result set ⇒ nothing downstream executes, including the counter bump.
    SELECT s.* FROM settled s
     WHERE s.energy_current >= @energy_cost::int * @times::int
       AND s.level          >= @required_level::int
),
bump AS (
    INSERT INTO player_job_stats AS pjs (player_id, job_id, collects)
    SELECT g.id, @job_id::text, @times::int FROM guard g
    ON CONFLICT (player_id, job_id)
    DO UPDATE SET collects = pjs.collects + @times::int
    RETURNING pjs.collects            -- total AFTER this batch
),
-- Per-collect milestone lookup: @ms_at = {25,50,100}, @ms_bp = {500,1000,1500}
award AS (
    SELECT
      COALESCE(SUM(
        ( @base_gold::bigint
          * (10000 + COALESCE((
                SELECT MAX(m.bp)
                  FROM unnest(@ms_at::int[], @ms_bp::int[]) AS m(at, bp)
                 WHERE b.collects - @times::int + g.i >= m.at
            ), 0)) / 10000
        ) * @gold_mult_bp::bigint / 10000
      ), 0)::bigint AS gold,
      (@base_xp::bigint * @times::int * @xp_mult_bp::bigint / 10000)::bigint AS xp,
      MAX(b.collects) AS collects
      FROM bump b, generate_series(1, @times::int) AS g(i)
),
upd AS (
    UPDATE players p SET
        energy_current     = p.energy_current - @energy_cost::int * @times::int,
        gold               = p.gold + a.gold,
        xp                 = p.xp   + a.xp,
        lifetime_gold      = p.lifetime_gold + a.gold,
        -- @level_xp is the CUMULATIVE xp threshold array from the config bundle
        level              = (SELECT count(*) FROM unnest(@level_xp::bigint[]) t
                               WHERE t <= p.xp + a.xp)::int,
        unspent_stat_points= p.unspent_stat_points
                             + ((SELECT count(*) FROM unnest(@level_xp::bigint[]) t
                                  WHERE t <= p.xp + a.xp)::int - p.level)
                               * @points_per_level::int,
        updated_at         = @now
      FROM guard g, award a
     WHERE p.id = g.id
    RETURNING p.*, a.gold AS gold_gain, a.xp AS xp_gain,
              a.collects AS job_collects, g.level AS old_level
),
led AS (
    INSERT INTO ledger (player_id, currency, delta, balance_after, reason,
                        ref_type, ref_id, idem_key, config_ver, created_at)
    SELECT u.id, 'gold', u.gold_gain, u.gold, 'collect',
           'job', NULL, @idem_key::text, @config_ver::int, @now
      FROM upd u
    UNION ALL
    SELECT u.id, 'xp', u.xp_gain, u.xp, 'collect',
           'job', NULL, @idem_key::text, @config_ver::int, @now
      FROM upd u
)
SELECT * FROM upd;
```

Zero rows returned ⇒ the guard failed. The service inspects the settled row (already in hand) to emit the precise error: `insufficient_energy` (with `required`/`have`) or `level_locked`.

The critical structural detail: **`bump` selects `FROM guard`.** Data-modifying CTEs in Postgres execute unconditionally *if they are not gated by an empty input relation* — writing `INSERT … VALUES (…)` there would increment the collect counter even on a failed collect. `INSERT … SELECT … FROM guard` inserts zero rows when the guard is empty.

Round trips for a collect: 1 (this statement) + 1 (idempotency claim) + 1 (idempotency complete) = **3**, ≈ 10 ms wall clock on DO LON1.

`times ∈ [1,10]` lets the client batch a burst of taps into one request — a large UX and cost win on mobile, and the `generate_series` term applies milestone thresholds correctly *per collect within the batch*.

## 7. Anti-cheat

### 7.1 What the server validates (the client sends intent only)

The client **never** sends an amount, a price, a stat, a tier, or a result. It sends `{job_id}`, `{offer_id}`, `{slot_index, soldier_type}`, `{item_id, target}`. Everything else is looked up in the server's active config bundle and the locked DB rows.

| Action | Server-side validation |
|---|---|
| Collect | job exists in bundle; `level ≥ job.unlock_level`; `energy ≥ cost×times`; `times ∈ [1,10]`; reward computed server-side |
| Family upgrade | key exists; `level < max_level`; cost from `cost_curve[level]`; `gold ≥ cost` |
| Stat allocate | `sum(points) ≤ unspent_stat_points`; each ≥ 0; no overflow |
| Shop buy | offer recomputed from the seed for the *current* window; window not expired; not already purchased; `gold ≥ price` |
| Recruit | slot index `< slots_owned`; slot empty; `gold ≥ price(type)`; tier drawn from the server keyring |
| Slot buy | `slots_owned < max_slots`; price from `slot_price_curve[slots_owned]` |
| Equip | item owned by caller; item not locked; item kind matches slot; soldier owned by caller; previous occupant unequipped in same tx |
| Sell | all item ids owned, unlocked, unequipped |
| Attack | offer HMAC valid and unexpired and issued to *this* attacker; `energy ≥ attack_cost`; defender not shielded; not self; not same kingdom; both past newbie shield; pair cooldown |
| Kingdom | role permits the action; membership caps; gold ≥ founding cost |
| IAP | Apple JWS signature chain verified; `transaction_id` unique |

Derived integrity fields (`players.power`, `soldiers.power`) are **recomputed server-side inside the same transaction** as any equip/recruit/dismiss/stat change — never accepted from the client, and re-verified by the nightly anomaly scan.

### 7.2 Replay protection

Three layers, no extra machinery: **TLS 1.3** (Caddy), **short-lived access tokens** (15 min), and **idempotency keys** (§6). A replayed request either carries a used key (→ stored response, no new effect) or an expired token (→ 401). There is no scenario where replay yields extra currency.

### 7.3 Request signing — not worth it

**Do not implement HMAC request signing.** The signing key would have to ship inside the Godot `.pck`, which is trivially unpacked with `gdsdecomp`; the effort buys hours of delay against one determined attacker and costs permanent engineering and debuggability. Certificate pinning is similarly weak (bypassed on any jailbroken device, and it breaks when Let's Encrypt rotates). **The real defence is that the server owns every number** — a fully-cheating client can only send valid intents faster, which is what rate limits and the faucet ceiling (§7.5) are for.

Two things that *are* worth it:
1. **`X-Client-Version` gate** now: a minimum-version list in the config bundle; below it → `426 Upgrade Required`. This is the kill switch for an exploitable build, and it costs 20 lines.
2. **Apple App Attest** at v1.1 (not v1): a hardware-backed attestation that the request comes from a genuine, unmodified build of your app on real Apple silicon. This is the only client-integrity mechanism with real teeth, and Apple provides it free. Add `POST /v1/attest/challenge` + `POST /v1/attest/register`, store the attested key per device, and require an assertion header on high-value endpoints (`/v1/attack`, `/v1/iap/*`, `/v1/soldiers/recruit`). Defer to v1.1 because it requires client plugin work.

### 7.4 The currency ledger

```sql
CREATE TABLE ledger (
    id            bigint      GENERATED ALWAYS AS IDENTITY,
    player_id     uuid        NOT NULL,
    currency      text        NOT NULL,   -- gold | diamonds | xp | reputation
    delta         bigint      NOT NULL,
    balance_after bigint      NOT NULL,
    reason        text        NOT NULL,   -- collect | tax_claim | shop_buy | recruit | slot_buy |
                                          -- sell | upgrade | pvp_steal | pvp_loss | iap | admin_adjust
    ref_type      text,
    ref_id        uuid,
    idem_key      text,
    config_ver    int         NOT NULL,
    created_at    timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE INDEX ledger_player_idx  ON ledger (player_id, created_at DESC);
CREATE INDEX ledger_reason_idx  ON ledger (reason, created_at DESC);
```

Monthly partitions, created 3 months ahead by the scheduler, detached and archived to R2 after 12 months. Append-only: `REVOKE UPDATE, DELETE ON ledger FROM emperors_app`. Corrections are **reversing entries**, never mutations.

Every currency movement writes a ledger row **in the same statement** as the balance change (see the `led` CTE in §6.4), so a balance can never move without a journal entry. PG18's `RETURNING OLD.gold, NEW.gold` is available if you prefer to derive `delta` in SQL rather than pass it.

**The invariant:** `SUM(ledger.delta) WHERE currency='gold' == players.gold`, for every player, always. This is asserted by the nightly reconciler and by `TestLedgerReconciles` (§13), and it is the single highest-value test in the codebase — it catches every class of accounting bug, including ones you didn't think to test.

### 7.5 The anomaly detector

A scheduler job every 15 minutes on the **direct** pool, `SET LOCAL statement_timeout='60s'`.

**(1) The faucet ceiling — the killer check.** Energy is the *only* input to gold from collecting, and the server owns energy regeneration. Therefore, for any window, the maximum honest gold from collect is a closed-form function of the player's regen period, cap, and best unlocked job:

```
max_gold(Δt) = ( Δt_ms / energy_period_ms + energy_max )        -- energy available in the window
             / best_job.energy_cost
             * best_job.base_gold
             * (10000 + max_total_multiplier_bp) / 10000
             * 1.05                                             -- slack for clock/boundary effects
```

```sql
-- anomaly: impossible collect income
SELECT l.player_id, SUM(l.delta) AS gained
  FROM ledger l
 WHERE l.currency = 'gold' AND l.reason = 'collect'
   AND l.created_at > $window_start
 GROUP BY l.player_id
HAVING SUM(l.delta) > $max_gold_per_player;   -- computed per-player in Go from their row + bundle
```
Any hit is *deterministically* either an exploit or a bug. Severity: critical.

**(2) Conservation.** 500 random players per run: `SUM(ledger.delta)` vs `players.gold`. Mismatch ⇒ P1 page (this is a bug, not a cheat).

**(3) Action rate.** `count(*) FROM ledger WHERE reason='collect' AND created_at > now()-'1 hour'` exceeding `3600000/energy_period_ms + burst`.

**(4) PvP alt-farming.** Attacker/defender pairs seen > N times per day; or an attacker whose last 20 defenders are all accounts created within 24 h from the same `/24` (join `devices.last_ip`).

**(5) Progression consistency.** `level` vs `lifetime_xp` against the level curve; `players.power` vs a fresh recomputation from owned items and stats; `diamonds` with no matching `iap` ledger rows.

**(6) Protocol signals.** 4xx rate per player, malformed idempotency keys, `X-Client-Version` outside the released set, requests with clock skew > 5 min.

Output:
```sql
CREATE TABLE anomaly_flags (
    id         uuid PRIMARY KEY DEFAULT uuidv7(),
    player_id  uuid NOT NULL REFERENCES players(id) ON DELETE CASCADE,
    kind       text NOT NULL,
    severity   smallint NOT NULL,        -- 1 info … 4 critical
    evidence   jsonb NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    resolved_at timestamptz,
    resolution text
);
```
Severity ≥ 3 posts to a Discord webhook and bumps `players.throttle_level`. Flagged players are excluded from leaderboards until resolved. The admin panel offers **"reverse ledger since T"** (writes compensating entries, never deletes) rather than a ban button — bans are the last resort because false positives cost real players.

## 8. PvP

### 8.1 Safe gold transfer between two players

**Global lock-ordering rule, enforced everywhere in the codebase: when a transaction must lock more than one `players` row, lock them in ascending `uuid` order.** Deadlock becomes structurally impossible: A-attacks-B and B-attacks-A both take `min(A,B)` first and serialize.

Do **not** rely on `SELECT … WHERE id = ANY($1) ORDER BY id FOR UPDATE` — Postgres acquires row locks during the scan, and the planner is free to choose a scan order that differs from the `ORDER BY`. Issue two separate locking statements in sorted order (each `app.settle_player` call *is* such a statement).

```go
// internal/service/pvp.go
func (s *PvP) Attack(ctx context.Context, tx pgx.Tx,
    attackerID uuid.UUID, offer rng.SignedOffer, now time.Time,
) (*domain.BattleResult, error) {

    q   := sqlcdb.New(tx)
    cfg := s.cfg.Load()

    // ---- 1. deterministic lock order -------------------------------------
    lo, hi := attackerID, offer.DefenderID
    if lo.Compare(hi) > 0 { lo, hi = hi, lo }          // Go 1.27 stdlib uuid.Compare

    rlo, err := q.SettlePlayer(ctx, toPG(lo), now)
    if err != nil { return nil, err }
    rhi, err := q.SettlePlayer(ctx, toPG(hi), now)     // no deadlock: global ascending order
    if err != nil { return nil, err }

    attacker, defender := rlo, rhi
    if lo != attackerID { attacker, defender = rhi, rlo }

    // ---- 2. re-validate EVERYTHING under lock (the offer is only a hint) --
    switch {
    case attacker.EnergyCurrent < cfg.PvP.EnergyCost:
        return nil, apperr.InsufficientEnergy(cfg.PvP.EnergyCost, attacker.EnergyCurrent)
    case defender.ShieldUntil.Valid && defender.ShieldUntil.Time.After(now):
        return nil, apperr.TargetShielded(defender.ShieldUntil.Time)
    case defender.KingdomID.Valid && defender.KingdomID == attacker.KingdomID:
        return nil, apperr.SameKingdom()
    case defender.NewbieUntil.After(now) || attacker.NewbieUntil.After(now):
        return nil, apperr.NewbieProtected()
    }
    recent, err := q.CountRecentBattles(ctx, attacker.ID, defender.ID,
        now.Add(-cfg.PvP.PairCooldown))
    if err != nil { return nil, err }
    if recent >= cfg.PvP.MaxPairAttacksPerWindow { return nil, apperr.TargetOnCooldown() }

    // ---- 3. deterministic, auditable combat ------------------------------
    battleID := uuid.NewV7()
    seed     := s.keys.Seed(rng.PurposeBattle, cfg.RNGVersion, battleID.String())

    aSnap, err := s.snapshotSide(ctx, q, attacker, cfg)   // player + soldiers + equipment, resolved
    if err != nil { return nil, err }
    dSnap, err := s.snapshotSide(ctx, q, defender, cfg)
    if err != nil { return nil, err }

    res := battle.Resolve(cfg, aSnap, dSnap, seed)        // PURE: no db, no clock, no randomness

    // ---- 4. move the gold ------------------------------------------------
    steal := int64(0)
    if res.AttackerWins {
        steal = defender.Gold * int64(cfg.PvP.StealBP) / 10000
        steal = min(steal, cfg.PvP.MaxStealPerAttack)
        steal = max(steal, 0)
    }

    // Guarded debit: 0 rows means the defender's gold moved under us -> retry the tx.
    dRow, err := q.PvPDebitDefender(ctx, sqlcdb.PvPDebitDefenderParams{
        ID: defender.ID, Amount: steal, Now: now,
        ShieldUntil: nullTime(!res.AttackerWins, now.Add(cfg.PvP.ShieldDuration)),
    })
    if err != nil { return nil, err }

    aRow, err := q.PvPCreditAttacker(ctx, sqlcdb.PvPCreditAttackerParams{
        ID: attacker.ID, Amount: steal, EnergyCost: cfg.PvP.EnergyCost,
        Reputation: res.ReputationGain, Now: now,
    })
    if err != nil { return nil, err }

    // ---- 5. journal, history, notification -------------------------------
    if err := q.InsertBattle(ctx, sqlcdb.InsertBattleParams{
        ID: toPG(battleID), AttackerID: attacker.ID, DefenderID: defender.ID,
        AttackerWon: res.AttackerWins, GoldStolen: steal,
        Snapshot: mustJSON(battleSnapshot{A: aSnap, D: dSnap}),
        Rounds:   mustJSON(res.Rounds),
        RNGVersion: int32(cfg.RNGVersion), ConfigVer: int32(cfg.Version),
        CreatedAt: now,
    }); err != nil { return nil, err }

    if steal > 0 {
        if err := s.ledger.Pair(ctx, q, ledger.Entry{
            Player: attacker.ID, Currency: "gold", Delta: +steal,
            BalanceAfter: aRow.Gold, Reason: "pvp_steal", RefType: "battle", RefID: battleID,
        }, ledger.Entry{
            Player: defender.ID, Currency: "gold", Delta: -steal,
            BalanceAfter: dRow.Gold, Reason: "pvp_loss", RefType: "battle", RefID: battleID,
        }, now, cfg.Version); err != nil { return nil, err }
    }
    if err := q.InsertNotification(ctx, defender.ID, "attacked",
        mustJSON(map[string]any{
            "battle_id": battleID, "by": attacker.Name,
            "gold_lost": steal, "won": !res.AttackerWins,
        }), now); err != nil { return nil, err }

    return res.WithIDs(battleID, steal, dRow.ShieldUntil), nil
}
```

### 8.2 Fair, cheap target selection at scale

**Stateless HMAC-signed offers. Zero database writes on `GET /v1/attack/targets`.**

A naive design writes 3 `pvp_offers` rows per refresh; at 100k DAU × 20 refreshes/day that is 6M rows/day of pure churn on Neon. Instead the server returns an opaque token:

```
offer = base64url(payload) + "." + base64url(HMAC-SHA256(pvp_offer_key, payload))
payload = {a: attacker_id, d: defender_id, exp: unix_ms, n: 8-byte nonce}
```

The token proves *"the server offered you this target within the last 5 minutes"*, which is all it needs to prove — it prevents target-shopping (scanning for the richest player) while everything that actually matters (shield, energy, kingdom, cooldown) is re-validated under lock at attack time. Single-use enforcement is not needed and not wanted: attacking the same player twice is legal if the rules permit, and the pair cooldown is enforced from the `battles` table we already write.

Candidate query — an index range scan around a random pivot inside the power band, O(log n + 20):

```sql
-- name: FindAttackTargets :many
WITH b AS (
    SELECT (@power::bigint * @lo_bp::int  / 10000) AS lo,
           (@power::bigint * @hi_bp::int / 10000) AS hi
),
p AS (SELECT lo + (floor(random() * GREATEST(1, hi - lo + 1)))::bigint AS pivot FROM b)
(
  SELECT pl.id, pl.name, pl.level, pl.power, pl.gold, pl.kingdom_id, pl.is_bot
    FROM players pl, p, b
   WHERE pl.power >= p.pivot AND pl.power <= b.hi
     AND pl.id <> @self_id
     AND pl.shield_until  <= @now
     AND pl.newbie_until  <= @now
     AND pl.deleted_at IS NULL
     AND pl.banned_at  IS NULL
     AND (pl.kingdom_id IS NULL OR pl.kingdom_id IS DISTINCT FROM @self_kingdom)
   ORDER BY pl.power ASC
   LIMIT 12
)
UNION ALL
(
  SELECT pl.id, pl.name, pl.level, pl.power, pl.gold, pl.kingdom_id, pl.is_bot
    FROM players pl, p, b
   WHERE pl.power < p.pivot AND pl.power >= b.lo
     AND pl.id <> @self_id
     AND pl.shield_until <= @now
     AND pl.newbie_until <= @now
     AND pl.deleted_at IS NULL
     AND pl.banned_at  IS NULL
     AND (pl.kingdom_id IS NULL OR pl.kingdom_id IS DISTINCT FROM @self_kingdom)
   ORDER BY pl.power DESC
   LIMIT 12
);
```

Go then filters out anyone attacked in the last 6 h (one indexed query against `battles`), shuffles with a request-local RNG, and returns 3. Band: `lo_bp = 8000`, `hi_bp = 12500` (0.80×–1.25× power), widening in two steps if fewer than 3 candidates are found, and finally falling back to bots.

**Fairness rules**, all enforced here and re-checked at attack time: no shielded targets, no kingdom-mates, no self, no newbies (< 24 h or < level 5), no banned/deleted, no repeat within the pair cooldown, power band both ways (you cannot farm the weak *or* be farmed by the strong).

**Bots.** At launch the population is too thin for a fair band. Seed ~2000 `is_bot` players across the power curve via an admin task; they can be attacked and their gold is synthetic (ledger `reason='bot'`, excluded from economy dashboards) and regenerates on a schedule. They never attack. Exclude them from leaderboards. Retire them by power band as real density grows.

The client's returned `gold_estimate_band` is a **bucket** (`"1k–5k"`), never the exact figure, so the target list is not a gold oracle.

### 8.3 Enforcing the 30-minute shield

**No cron, no expiry job.** `players.shield_until timestamptz NOT NULL DEFAULT '-infinity'`.

- **Set:** only when the *defender loses* — `shield_until = now + interval '30 minutes'` inside the attack transaction (see `PvPDebitDefender`).
- **Enforce:** `shield_until <= @now` in the matchmaking query (so shielded players are invisible), *and* re-checked under lock in `Attack` (so a shield acquired between offer and attack is honoured).
- **Expire:** implicitly. A past timestamp compares false; nothing needs to clean it up.
- **Extend (future diamond purchase):** `shield_until = GREATEST(shield_until, now) + duration` — so buying while shielded stacks rather than truncates.
- **Display:** `/v1/state` returns `shield_until` and the client counts down locally against `server_time_ms`.

Same trick for `newbie_until`. This is the general principle: **an expiring state is a timestamp compared on read, never a row that must be swept.**

## 9. Deterministic seeded RNG

### 9.1 PRNG choice

**`math/rand/v2` with `rand.NewChaCha8(seed [32]byte)`.** Rejected: `rand.NewPCG(a, b uint64)` — it accepts only 128 bits of seed (discarding half our HMAC digest) and, more importantly, its state is small enough that a player who observes a handful of outputs can in principle recover it and **predict future recruit tiers and shop rolls**. Shop windows are publicly predictable in time, so this is a live concern, not a theoretical one. ChaCha8 takes our full 32-byte digest, is cryptographically strong (outputs leak nothing about state), and costs ~1 ns/word — irrelevant next to a DB round trip.

### 9.2 Seed derivation

Server-held secrets, never client input, never `time.Now()` directly:

```go
// internal/game/rng/keyring.go
package rng

type Purpose string

const (
    PurposeShop    Purpose = "shop"
    PurposeRecruit Purpose = "recruit"
    PurposeBattle  Purpose = "battle"
    PurposeDrop    Purpose = "drop"
)

// Keyring holds one 32-byte secret per purpose, loaded from env at boot.
type Keyring struct{ keys map[Purpose][]byte }

// Seed is domain-separated by purpose and versioned by the bundle's RNGVersion,
// so changing the draw sequence requires an explicit version bump.
func (k *Keyring) Seed(p Purpose, rngVersion int, parts ...string) [32]byte {
    m := hmac.New(sha256.New, k.keys[p])
    fmt.Fprintf(m, "emperors|v%d|%s", rngVersion, p)
    for _, s := range parts {
        m.Write([]byte{0x1f})            // unit separator: prevents "ab"+"c" == "a"+"bc"
        m.Write([]byte(s))
    }
    var out [32]byte
    copy(out[:], m.Sum(nil))
    return out
}

func New(seed [32]byte) *rand.Rand { return rand.New(rand.NewChaCha8(seed)) }
```

| Roll | Seed inputs | Anti-reroll mechanism |
|---|---|---|
| **Shop** | `player_id`, `window` = `floor(unix_sec / 300)`, `reroll_counter` | Purely derived from time; retrying `GET /v1/shop` in the same window is bit-identical. There is nothing to reroll. |
| **Paid reroll** | same, with `reroll_counter + 1` | The counter is incremented and committed in the same transaction that charges diamonds; a retry with the same idempotency key replays the stored response. |
| **Recruit** | `player_id`, `recruit_seq` | `UPDATE players SET recruit_seq = recruit_seq + 1 … RETURNING recruit_seq` inside the transaction. The outcome is bound to a specific counter value that is consumed atomically. |
| **Battle** | `battle_id` (`uuidv7`, server-generated in-tx) | The battle row and its result commit together. |
| **Item stat roll** | `item_id` (server-generated) | Same. |

**Why a player cannot reroll by retrying.** For the shop, the roll is a pure function of `(player, time window, reroll counter)` — there is no request whose retry changes it. For recruits, the seed comes from a monotonic counter incremented *inside the transaction*: the client cannot observe the result before commit (the response is only produced after commit), so there is no point at which it could abort to avoid a bad tier. A force-quit mid-request leaves the soldier created and visible on the next `/v1/state`. And a retry carrying the same `Idempotency-Key` returns the stored response without touching the counter; a retry with a *new* key is a genuinely new purchase that costs gold again — which is the correct semantics.

### 9.3 Shop roll

```go
// internal/game/items/shop.go  — PURE
func RollShop(cfg *gameconfig.Bundle, kr *rng.Keyring,
    playerID uuid.UUID, window int64, reroll int32) []Offer {

    seed := kr.Seed(rng.PurposeShop, cfg.RNGVersion,
        playerID.String(), strconv.FormatInt(window, 10), strconv.Itoa(int(reroll)))
    r := rng.New(seed)

    offers := make([]Offer, 0, cfg.Shop.SlotCount)
    for i := 0; i < cfg.Shop.SlotCount; i++ {
        // DRAW ORDER IS PART OF THE CONTRACT. Never reorder without bumping RNGVersion.
        kind   := pickWeighted(r, cfg.Shop.KindWeights)     // []Weight, fixed order — NEVER a map
        rarity := pickWeighted(r, cfg.Shop.RarityWeights)   // []Weight, fixed order

        pool := cfg.TemplatesFor(kind, rarity)              // pre-sorted by TemplateID at load time
        t    := pool[int(r.Uint64()%uint64(len(pool)))]

        span   := cfg.Item.StatRollMaxBP - cfg.Item.StatRollMinBP + 1
        rollBP := int64(cfg.Item.StatRollMinBP) + int64(r.Uint64()%uint64(span))

        offers = append(offers, Offer{
            Index: i, TemplateID: t.ID, Kind: kind, Rarity: rarity, RollBP: rollBP,
            Attack:  t.BaseAttack  * rollBP / 10000,
            Defense: t.BaseDefense * rollBP / 10000,
            Price:   cfg.Shop.PriceFor(rarity, kind),
        })
    }
    return offers
}

func pickWeighted(r *rand.Rand, ws []gameconfig.Weight) string {
    total := 0
    for _, w := range ws { total += w.BP }
    n := int(r.Uint64() % uint64(total))
    for _, w := range ws {
        if n < w.BP { return w.Key }
        n -= w.BP
    }
    return ws[len(ws)-1].Key
}
```

**Two reproducibility landmines, both fatal and both easy to hit:**
1. **Never iterate a Go map to build a weight table or a template pool.** Map iteration order is randomised per process; the same seed would produce different shops on different servers. `gameconfig.Load` must deserialise weights into ordered slices and `sort.Slice` every template pool by ID. Assert this in the loader with a `slices.IsSortedFunc` check.
2. **Never change the number or order of `r.Uint64()` calls** for a given `RNGVersion`. Adding a draw shifts every subsequent value. Golden tests (§13) fail loudly if you do; the fix is to bump `cfg.RNGVersion`, which changes every seed and is therefore a deliberate act.

`RollShop` is called on `GET /v1/shop` (pure computation, **zero DB writes**) and again on `POST /v1/shop/buy` to re-derive and validate the offer at index `i`. Purchases are recorded so an offer cannot be bought twice:

```sql
CREATE TABLE shop_purchases (
    player_id  uuid   NOT NULL REFERENCES players(id) ON DELETE CASCADE,
    window_id  bigint NOT NULL,
    reroll     int    NOT NULL,
    slot_index int    NOT NULL,
    item_id    uuid   NOT NULL REFERENCES items(id),
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (player_id, window_id, reroll, slot_index)
);
```
Buying does `INSERT … ON CONFLICT DO NOTHING RETURNING`; zero rows means already purchased → `409 offer_already_purchased`. GC rows older than 24 h.

That the shop costs **zero writes until a purchase** is a significant scaling property: it is the most-polled endpoint in the game.

### 9.4 Soldier recruit

```go
func RollRecruit(cfg *gameconfig.Bundle, kr *rng.Keyring,
    playerID uuid.UUID, recruitSeq int64, kind string) Recruit {

    seed := kr.Seed(rng.PurposeRecruit, cfg.RNGVersion,
        playerID.String(), strconv.FormatInt(recruitSeq, 10))
    r := rng.New(seed)

    st     := cfg.SoldierTypes[kind]                  // ordered lookup, validated at load
    rarity := pickWeighted(r, st.RarityWeights)       // peasant/mercenary/gladiator differ here
    span   := st.StatRollMaxBP - st.StatRollMinBP + 1
    rollBP := int64(st.StatRollMinBP) + int64(r.Uint64()%uint64(span))
    tier   := cfg.Rarities[rarity]

    return Recruit{
        Kind: kind, Rarity: rarity, RollBP: rollBP,
        BaseAttack:  st.BaseAttack  * tier.StatMultBP / 10000 * rollBP / 10000,
        BaseDefense: st.BaseDefense * tier.StatMultBP / 10000 * rollBP / 10000,
    }
}
```

**Key rotation caveat.** Rotating `SEED_KEY_RECRUIT` or `SEED_KEY_BATTLE` is harmless — those outcomes are materialised as rows the moment they happen. Rotating `SEED_KEY_SHOP` mid-window would silently change every player's *currently displayed* shop, which is a bad experience (an item you were about to buy vanishes). Rotate shop keys only via a versioned keyring (`shop_key_v2`) whose version is folded into `window_id`, or simply never rotate it. Documented in the runbook.

## 10. API surface

Base: `https://api.emperors.<domain>/v1`. `Content-Type: application/json; charset=utf-8`.

**Request headers:** `Authorization: Bearer <jwt>`, `Idempotency-Key` (mutating routes), `X-Client-Version: 1.4.2 (ios)`, `X-Config-Version: 42`, `Accept-Encoding: gzip`.

**Response headers (every response):** `X-Request-Id`, `X-Config-Version`, `X-Server-Time-Ms`; plus `Idempotent-Replay: true` on replays and `X-Config-Stale: true` when the client's config version is behind.

**Error envelope:**
```json
{ "error": { "code": "insufficient_energy",
             "message": "Not enough energy.",
             "details": { "required": 5, "have": 3, "full_at": "2026-09-04T18:21:03Z" },
             "request_id": "0199…" } }
```

**Error codes** (stable, client-switchable): `unauthenticated`, `token_expired`, `forbidden`, `not_found`, `validation_failed`, `insufficient_energy`, `insufficient_gold`, `insufficient_diamonds`, `level_locked`, `slot_occupied`, `slot_not_owned`, `max_level_reached`, `offer_expired`, `offer_already_purchased`, `target_shielded`, `target_on_cooldown`, `same_kingdom`, `newbie_protected`, `self_attack`, `not_kingdom_member`, `insufficient_role`, `kingdom_full`, `name_taken`, `name_rejected`, `idempotency_key_required`, `idempotency_key_reuse`, `request_in_flight`, `rate_limited`, `upgrade_required`, `try_again`, `internal`.

**JSON number rule (client-critical).** GDScript's JSON parser is float-backed for large values; anything that can exceed 2^53 is serialised as a **string**: `gold`, `diamonds`, `xp`, `lifetime_gold`, `reputation`, `power`, all prices and rewards. Small bounded integers (`level`, `energy_current`, `energy_max`, counts, basis points) stay as JSON numbers. All UUIDs are strings. Enforced by a custom `type Amount int64` with `MarshalJSON`/`UnmarshalJSON` in `internal/domain`.

**Pagination:** cursor-based only. `?cursor=<opaque base64 of (sort_key,id)>&limit=50`. Never `OFFSET`.

## 11. Realtime

**No WebSockets in v1. Decisive.**

1. **Nothing in the game is synchronous.** PvP is asynchronous by design; there is never a live opponent.
2. **The lazy-accrual model makes push unnecessary.** The client receives `(energy_current, energy_period_ms, energy_anchor_at, server_time_ms)` and renders a perfectly accurate ticking counter locally, forever, with zero further traffic. Pushing energy updates would be pure waste.
3. **Config changes** propagate via the `X-Config-Version` header already present on every response — the client sees a bump on its next request and refetches `/v1/config`. Free push channel, zero infrastructure.
4. **"You were attacked while offline"** arrives in `state.notifications` at next open. Real-time delivery, when we want it, belongs on **APNs**, not a socket — a socket only reaches users who already have the app open, which is precisely the population that doesn't need it.
5. **Costs avoided:** connection state in a stateless binary, heartbeats, GDScript reconnect logic, and — significantly — a blue/green deploy that must drain long-lived connections instead of finishing in-flight requests in 30 s.

**Revisit when:** live kingdom chat ships, or a synchronous co-op raid mode. Even then, kingdom chat at this scale is fine on 5-second polling or long-polling before it justifies a socket layer. If it does, use `github.com/coder/websocket v1.8.15` (context-aware, no `gorilla` baggage) on a dedicated `/v1/ws` route with its own goroutine budget.

**Clock rule:** every response carries `X-Server-Time-Ms` / `server_time_ms`. The client computes `offset = server_time - local_time` once per response and renders all countdowns against the corrected clock. It must **never** trust the device clock — changing the device date is the oldest idle-game cheat, and here it accomplishes exactly nothing because all accrual is computed from `timestamptz` anchors on the server.

## 12. Config delivery

### Storage

```sql
CREATE TABLE config_versions (
    id           int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    status       text NOT NULL CHECK (status IN ('draft','active','archived')),
    rng_version  int  NOT NULL DEFAULT 1,
    notes        text NOT NULL DEFAULT '',
    created_by   uuid,
    created_at   timestamptz NOT NULL DEFAULT now(),
    published_at timestamptz
);
CREATE UNIQUE INDEX config_one_active ON config_versions ((status)) WHERE status = 'active';

CREATE TABLE config_entries (
    version_id int  NOT NULL REFERENCES config_versions(id) ON DELETE CASCADE,
    kind       text NOT NULL,   -- job | family_upgrade | kingdom_upgrade | item_template |
                                -- rarity | soldier_type | level_curve | shop | pvp | economy | limits
    key        text NOT NULL,
    data       jsonb NOT NULL,
    sort_order int  NOT NULL DEFAULT 0,
    PRIMARY KEY (version_id, kind, key)
);
```

The partial unique index guarantees exactly one active version at any time.

### Publish flow

1. Admin clones the active version into a draft, edits entries in the Next.js panel.
2. `POST /admin/config/{id}/simulate` runs `cmd/simulate`'s engine server-side and returns a progression diff ("level 30 now takes 12 days, was 9; gold/hour at level 20 +18%"). This is the feature that prevents a bad balance patch from shipping — build it early.
3. `POST /admin/config/{id}/publish` runs the **validator** in a transaction: every referenced id exists; cost curves are monotonically non-decreasing; no negative rates; rarity weights sum to 10000 per table; every job's `unlock_level` is reachable on the level curve; item templates exist for every (kind, rarity) pair the shop can roll; no `rng_version` change without an explicit flag. On success it flips `status` and records an `admin_audit` row.

### Serving

The server holds an `atomic.Pointer[Bundle]`. A goroutine polls `SELECT id, rng_version FROM config_versions WHERE status='active'` **every 30 seconds** (one trivial indexed query — far simpler than `LISTEN/NOTIFY`, which is forbidden on the pooled endpoint anyway). On change it loads, validates, precomputes derived maps and sorted template pools, **pre-gzips the JSON once**, and swaps the pointer. Serving `/v1/config` is then a `bytes` copy.

```go
type ServedBundle struct {
    Version   int
    RNGVersion int
    Bundle    *Bundle
    JSON      []byte   // canonical, sorted keys
    GZIP      []byte   // pre-compressed once at swap time
    ETag      string   // `"cfg-42-a1b2c3d4e5f6"` = version + first 12 hex of sha256(JSON)
}
```

```
GET /v1/config
  200 OK
  ETag: "cfg-42-a1b2c3d4e5f6"
  Cache-Control: public, max-age=60, stale-while-revalidate=600
  Content-Encoding: gzip           (only if Accept-Encoding includes gzip)
  Vary: Accept-Encoding

GET /v1/config          If-None-Match: "cfg-42-a1b2c3d4e5f6"
  304 Not Modified

GET /v1/config?v=42                # immutable, CDN-friendly, for pinning a specific version
  Cache-Control: public, max-age=31536000, immutable
```

Estimated size: ~50 jobs + ~60 upgrades + ~200 item templates + 7 rarities + 3 soldier types + curves ≈ 120 KB JSON, ~18 KB gzipped. Cheap enough to fetch on every cold start.

**Version skew policy — never reject a stale client.** If a request arrives with an old `X-Config-Version`, execute it at **server** prices anyway and return `X-Config-Stale: true`. The client then refetches `/v1/config` and re-renders. Rejecting would break every in-flight player the instant a balance patch publishes, which is unacceptable for a live game. Every ledger row records `config_ver`, so an audit can always reconstruct which prices applied.

**Assets are not in the bundle.** Entries carry an `icon_key` that maps to an atlas region shipped in the Godot `.pck`, plus an optional `icon_url` fallback so items added after a client release still render (served from `/assets/` by Caddy, or a CDN). The client falls back to a rarity-coloured placeholder if it knows neither — so a new item is never an invisible item.

**Rarity colours live in the bundle** (`{"code":"epic","color_hex":"#8B5CF6","name":"Epic"}`), which means the epic/mystic colour conflict is fixable from the admin panel without a client release.

## 13. Observability

**Logging — `log/slog` (stdlib), JSON handler, to stdout.** No third-party logger. Every log line carries `request_id`, `player_id` (when authenticated), `route`, `config_version`, `service`, `version`, `commit`. A `slog.Handler` wrapper pulls these from the context so call sites stay clean. Levels: `INFO` for one line per request; `WARN` for 4xx that indicate client bugs; `ERROR` for 5xx only. Business events (`level_up`, `kingdom_founded`, `iap_granted`, `anomaly_flagged`) are logged at `INFO` with `event=` so they're queryable.

**Metrics — `github.com/prometheus/client_golang v1.24.1`** on a second `http.Server` bound to `127.0.0.1:9090` (never exposed through Caddy).

- HTTP: `http_requests_total{route,method,status}`, `http_request_duration_seconds{route}` (histogram), `http_in_flight`.
- DB: `db_query_duration_seconds{query}` via a pgx `QueryTracer`; a custom collector exporting `pool.Stat()` (`AcquiredConns`, `IdleConns`, `EmptyAcquireCount`, `CanceledAcquireCount`, `NewConnsCount`).
- Runtime: `go_*` + `process_*` (default collectors).
- **Game (the ones that actually matter):**
  - `game_gold_minted_total{reason}` and `game_gold_burned_total{reason}` — a live faucet/sink dashboard. If minting outruns burning for a week, the economy is inflating and you know before players do. **This is the single most valuable dashboard in the project.**
  - `game_collects_total{job}`, `game_attacks_total{result}`, `game_recruits_total{kind,rarity}`, `game_shop_purchases_total{rarity}`
  - `game_active_players` (5-minute unique gauge), `game_new_players_total`
  - `game_settle_duration_seconds`, `game_idempotency_replays_total`, `game_rate_limited_total{route}`, `game_tx_retries_total{code}`
  - `game_anomaly_flags_total{kind,severity}`

**Errors — `github.com/getsentry/sentry-go v0.49.0`.** Wired into the `Recover` middleware and into the 5xx path of the error writer (4xx are never sent — they'd drown the quota). Tags: `request_id`, `player_id`, `route`, `config_version`, `release` (= git SHA, so Sentry links stack traces to source). Free tier is 5k errors/month, comfortably enough.

**Where it ships — Grafana Cloud free tier** (10k active series, 50 GB logs, 14-day retention) with **Grafana Alloy** in the compose file scraping `127.0.0.1:9090` and tailing the Docker JSON logs. Rationale: self-hosting Prometheus + Loki + Grafana on a 4 GB VPS costs ~2 GB of RAM and becomes your problem at 3 a.m.; the free tier costs nothing and gives real alerting. If you later want full self-hosting, the Alloy config swaps two endpoints.

**Alerts (Grafana Cloud):** 5xx rate > 1% over 5 min; p99 latency > 1 s; `readyz` failing; pool `EmptyAcquireCount` rising; `game_gold_minted_total` 1-hour rate > 3× trailing 7-day median; any `severity=4` anomaly flag; Neon connection errors; disk > 80%.

**Uptime:** an external HTTP check (UptimeRobot/BetterStack free) on `/healthz` every minute from two regions.

**Tracing — deferred, but wired.** With one service and one database, route-level histograms plus per-query DB timings answer every question a trace would. `github.com/exaring/otelpgx v0.11.1` + `go.opentelemetry.io/otel v1.46.0` are added behind an `OTEL_ENABLED` flag so turning tracing on later is a config change, not a refactor.

## 14. Deployment

### Dockerfile (multi-stage, distroless)

```dockerfile
# syntax=docker/dockerfile:1.7
FROM golang:1.27-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download
COPY . .
ARG VERSION=dev
ARG COMMIT=none
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath \
      -ldflags="-s -w -X main.version=${VERSION} -X main.commit=${COMMIT}" \
      -o /out/api ./cmd/api

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/api /api
COPY --from=build /usr/share/zoneinfo /usr/share/zoneinfo
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/api"]
```

**Why `distroless/static-debian12:nonroot`:** a `CGO_ENABLED=0` binary needs only CA certificates (we make outbound TLS calls to Apple's JWKS, Google's certs, Sentry) — distroless/static ships them. ~25 MB total, no shell, no package manager, no libc CVEs, runs as UID 65532. **Rejected `alpine`** (musl DNS resolver quirks under load, a shell for an attacker, larger). **Rejected `scratch`** (no CA bundle → Apple Sign-In verification fails at runtime with a confusing error). Migrations embed via `embed.FS` and run through `cmd/api --migrate-only`, so no goose binary is needed in the image.

**Build `linux/amd64` only, and build it in CI, not on the dev machine** — the Mac is arm64 and cross-building locally through QEMU is slow and drift-prone.

### Zero-downtime deploy (`deploy/deploy.sh`, run over SSH by CI)

```bash
set -euo pipefail
cd /srv/emperors
export IMAGE_TAG="$1"

CUR=$(grep -o 'api-[a-z]*' upstream.caddy)          # api-blue
NEW=$([ "$CUR" = "api-blue" ] && echo api-green || echo api-blue)

docker compose pull "$NEW"

# 1. Migrate FIRST, against the DIRECT endpoint. Must be backward-compatible (expand/contract).
docker compose run --rm -e DATABASE_URL="$DATABASE_URL_DIRECT" "$NEW" --migrate-only

# 2. Start the idle colour and wait for real readiness.
docker compose --profile green up -d "$NEW"
for i in $(seq 1 30); do
  docker compose exec -T "$NEW" /api --healthcheck && break
  [ "$i" = 30 ] && { docker compose stop "$NEW"; echo "readiness failed"; exit 1; }
  sleep 1
done

# 3. Flip the upstream and reload Caddy gracefully.
echo "reverse_proxy $NEW:8080" > upstream.caddy
docker compose exec -T caddy caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile

# 4. Drain, then stop the old colour.
sleep 30
docker compose stop "$CUR"
docker image prune -f
```

Rollback is the same script with the previous tag; the old image is still on disk, so it takes ~15 seconds.

**Graceful shutdown in Go — the part people get wrong:**

```go
ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, syscall.SIGINT)
defer stop()
<-ctx.Done()

readiness.Store(false)                       // /readyz → 503 IMMEDIATELY, /healthz stays 200
time.Sleep(3 * time.Second)                  // let Caddy notice and stop routing here
sctx, cancel := context.WithTimeout(context.Background(), 25*time.Second)
defer cancel()
_ = srv.Shutdown(sctx)                       // finish in-flight requests
pools.RW.Close(); pools.Direct.Close()
sentry.Flush(2 * time.Second)
```

`stop_grace_period: 35s` in compose gives that sequence room. The `/readyz`-before-`/healthz` distinction is what prevents the ~1 s of 502s that naive blue/green produces.

### Secrets — SOPS + age

Do **not** put secrets in GitHub Actions and echo them over SSH. Commit `deploy/secrets.env.age`, encrypted with [`age`](https://age-encryption.org) via `sops`; the private key exists only at `/root/.config/sops/age/keys.txt` on the VPS. `deploy.sh` runs `sops -d secrets.env.age > .env && chmod 600 .env`. CI needs only an SSH deploy key and a GHCR token — nothing that can decrypt production. Every secret rotation is a reviewable, auditable commit.

### Backups

2. **Secondary: nightly logical dump, off-provider.** A GitHub Actions scheduled job (not the VPS — you want the backup to survive losing the VPS):
   ```bash
   pg_dump --no-owner --no-acl -Fc "$DATABASE_URL_DIRECT" \
     | age -r "$BACKUP_AGE_PUBKEY" \
   ```

3. **Monthly restore drill, automated.** Create a Neon branch, restore the newest dump into it, run the integration suite against it, assert `SUM(ledger.delta) == players.gold` for a sample, then delete the branch. **A backup you have never restored is not a backup.**
4. **Staging = a Neon branch of production.** Copy-on-write, instant, real data volumes. Rehearse every migration there first.

### Do we want Redis?

**No Redis in v1.** Every candidate use has a better answer here:

| Candidate | Verdict |
|---|---|
| Session store | Refresh tokens in Postgres + stateless JWT access tokens. Postgres already has the durability we need; Redis would add a second source of truth for auth. |
| Rate limiting | In-process `x/time/rate` + LRU. Correct and free on a single node. |
| Leaderboards | A `players (power DESC)` index makes `ORDER BY power DESC LIMIT 100` sub-millisecond at <1M rows; cache the result in-process for 60 s. A Redis ZSET solves a problem we don't have. |
| Config cache | `atomic.Pointer[Bundle]` in-process. |
| Shop state | Derived from a seed. Nothing to store. |
| Job queue | No async work in v1. |
| Cross-node invalidation | There is one node. |

**Adopt Redis the day we run a second app container** — for shared rate limiting (`throttled/v2` GCRA) and session-revocation pub/sub — and adopt **River v0.47.0** the day we ship APNs push or IAP webhook retries (note: River's *work coordinator* needs `LISTEN/NOTIFY`, so point it at the **direct** endpoint, or run it in poll-only mode).

### Scheduled work without a scheduler service

One goroutine in `cmd/api` with a ticker, each job wrapped in `pg_advisory_xact_lock(hashtext($job))` — **transaction-scoped**, therefore safe on the pooled endpoint — so overlapping blue/green containers can't double-run:

| Job | Cadence |
|---|---|
| Config version poll | 30 s |
| Leaderboard snapshot refresh | 60 s |
| Kingdom reputation roll-up (`SUM(kingdom_members.reputation_contributed)` → `kingdoms.reputation`) | 60 s |

### Layer 1 — pure unit tests on `internal/game` (fast, the bulk of the suite)

Because `internal/game` has no `context`, no DB and no clock, its tests are microseconds each. Table-driven coverage of `ComputeCollectReward`, `MilestoneBP`, `LevelForXP`, `UpgradeCost`, `DeriveRates`, `ItemPower`, `SoldierStats`, `battle.Resolve`, `RollShop`, `RollRecruit`.

## 16. Auth — full detail

### Device-based anonymous accounts

First launch: the Godot client generates 32 random bytes, base64url-encodes them into a `device_secret`, and **stores it in the iOS Keychain** (not `user://`, which is wiped on uninstall — Keychain items survive reinstall, so a player who deletes and reinstalls keeps their kingdom). It then calls:

```
POST /v1/auth/device
{ "device_secret": "…43 chars…", "platform": "ios", "app_version": "1.0.0",
  "device_model": "iPhone17,2", "locale": "tr-TR" }
```

Server stores only `sha256(device_secret)` — never the plaintext, so a database leak does not yield account credentials.

```sql
CREATE TABLE devices (
    id             uuid PRIMARY KEY DEFAULT uuidv7(),
    player_id      uuid NOT NULL REFERENCES players(id) ON DELETE CASCADE,
    secret_sha256  bytea NOT NULL UNIQUE,
    platform       text  NOT NULL,
    device_model   text,
    first_seen_at  timestamptz NOT NULL DEFAULT now(),
    last_seen_at   timestamptz NOT NULL DEFAULT now(),
    last_ip        inet,
    revoked_at     timestamptz
);
```

`INSERT … ON CONFLICT (secret_sha256) DO UPDATE SET last_seen_at = …, last_ip = … RETURNING player_id, (xmax = 0) AS is_new` makes the endpoint naturally idempotent — hence no idempotency key.

**Why not a device keypair?** Ed25519 challenge-response would be strictly better, but Godot 4's `Crypto` class offers RSA, not Ed25519, and RSA-2048 keygen in GDScript costs ~1 s on first launch. More importantly, the private key would live in the same Keychain as the secret, so the threat model is identical: both require device compromise. Ship the simple version; App Attest (§7.3) is the upgrade that actually adds security, not a device keypair.

**Abuse control:** `POST /v1/auth/device` is limited to 5/min and 30/hour per `/24`, and every new account gets `newbie_until = now + 24h` and cannot attack or be attacked until level 5. **This is what kills alt-farming**, which is otherwise the dominant exploit in a 3%-steal PvP game.

### Token scheme

**Access token: JWT, Ed25519 (EdDSA), 15 minutes, `github.com/golang-jwt/jwt/v5 v5.3.1`.**

```jsonc
{ "iss":"emperors", "aud":"game", "sub":"<player uuid>",
  "sid":"<session uuid>", "ver": 3, "iat":…, "exp":…, "jti":"…" }
```
Header carries `kid` for rotation.

- **Why JWT for access:** verification is a ~30 µs signature check with no DB round trip. At 1–2 ms RTT to Neon, adding a lookup to every request would raise p50 by ~20% for no benefit.
- **Why Ed25519 rather than HS256:** the Next.js admin panel (and any future service) can verify tokens with the *public* key alone; only the API holds the private key. Rotation is a `kid` lookup against `JWT_KEYS_JSON` — sign with the newest key, verify against any key whose `not_after` hasn't passed.

**Refresh token: opaque, 32 random bytes, stored hashed in Postgres, 60 days, rotating, with reuse detection.**

```sql
CREATE TABLE sessions (
    id            uuid PRIMARY KEY DEFAULT uuidv7(),
    player_id     uuid NOT NULL REFERENCES players(id) ON DELETE CASCADE,
    device_id     uuid REFERENCES devices(id) ON DELETE SET NULL,
    family_id     uuid NOT NULL,                  -- one lineage per device login
    token_sha256  bytea NOT NULL UNIQUE,
    prev_id       uuid REFERENCES sessions(id),
    created_at    timestamptz NOT NULL DEFAULT now(),
    expires_at    timestamptz NOT NULL,
    used_at       timestamptz,                    -- set when this token is exchanged
    revoked_at    timestamptz,
    user_agent    text,
    ip            inet
);
CREATE INDEX sessions_family_idx  ON sessions (family_id);
CREATE INDEX sessions_expiry_idx  ON sessions (expires_at) WHERE revoked_at IS NULL;
```

- **Why opaque and in Postgres:** revocation must be *real*. A stateless refresh JWT cannot be revoked, which is unacceptable for a token with a 60-day life on a stolen device.
- **Rotation:** every `/v1/auth/refresh` marks the presented row `used_at = now()` and issues a new row with `prev_id` set and the same `family_id`.
- **Reuse detection:** if a token that already has `used_at` is presented again, the family has leaked (an attacker replayed a stolen token). Revoke **the entire family** (`UPDATE sessions SET revoked_at = now() WHERE family_id = $1 AND revoked_at IS NULL`), bump `players.token_version`, log a `severity=3` anomaly, and force the device back through `/v1/auth/device`. This is the industry-standard construction and it costs one extra column.

**Revoking access tokens inside their 15-minute window:** `players.token_version` is embedded as the `ver` claim. Bumping it invalidates every outstanding access token. The API keeps a small in-process map of `player_id → token_version` for players whose version changed in the last 15 minutes, refreshed from a `token_revocations` table every 10 seconds. On a single node that is ~1 query per 10 s. (When we go multi-node: Redis pub/sub.)

### Linking to Apple / Google

```sql
CREATE TABLE identities (
    id          uuid PRIMARY KEY DEFAULT uuidv7(),
    player_id   uuid NOT NULL REFERENCES players(id) ON DELETE CASCADE,
    provider    text NOT NULL CHECK (provider IN ('apple','google')),
    subject     text NOT NULL,
    email       text,
    linked_at   timestamptz NOT NULL DEFAULT now(),
    UNIQUE (provider, subject)
);
```

Flow: `GET /v1/auth/nonce` returns a random nonce (stored hashed, 5-minute TTL, single use). The client passes it into `ASAuthorizationAppleIDRequest.nonce` (Apple expects the **SHA-256** of the nonce) and posts the resulting `identity_token`.

Verification — do it ourselves with `github.com/MicahParks/keyfunc/v3 v3.8.1` + `golang-jwt/v5`, not a wrapper library:
- Fetch and cache JWKS from `https://appleid.apple.com/auth/keys` (keyfunc refreshes automatically on unknown `kid`; cache 15 min).
- Assert `alg = RS256` (never accept `none` or the token's self-declared alg).
- `iss == "https://appleid.apple.com"`, `aud == APPLE_BUNDLE_ID`, `exp` in the future, `iat` recent, `nonce` matches the stored, unconsumed nonce.
- Google: JWKS at `https://www.googleapis.com/oauth2/v3/certs`, `iss ∈ {"accounts.google.com","https://accounts.google.com"}`, `aud == GOOGLE_CLIENT_ID`.

Then `INSERT INTO identities … ON CONFLICT (provider, subject) DO NOTHING RETURNING player_id`.

**The conflict case is a real product decision, not an error.** If that Apple `sub` already maps to a *different* player (the user reinstalled and played anonymously before signing in), return `409 identity_conflict` with summaries of both accounts:

```json
{ "error": { "code": "identity_conflict", "details": {
    "existing": { "player_id":"…","name":"Yigit","level":41,"power":"18200","last_seen":"…" },
    "current":  { "player_id":"…","name":"Guest","level":3,"power":"120","last_seen":"…" } } } }
```

The client shows "You already have an account — which one do you want to keep?" and calls `POST /v1/auth/link/resolve {provider, keep}`. Keeping `existing` re-points the device to that player, soft-deletes the current one (`deleted_at`, retained 30 days for support), revokes the old session family, and returns a fresh token pair. Do **not** attempt automatic account merging — merging two inventories, soldier rosters and kingdom memberships is a bug factory, and the "keep one" flow is what every comparable game ships.

## Key decisions

- **Host the API on DigitalOcean LON1, not Hetzner**
  - Rejected: Hetzner Falkenstein/Nuremberg (the cheaper default)
  - Why: Neon is in eu-west-2 (London). Hetzner has no London region; Falkenstein→London is ~15–18 ms RTT versus ~1–2 ms from DO LON1. At 3 DB round trips per mutating request that is 50 ms of pure network on every tap. If Hetzner is required for cost, move the Neon project to eu-central-1 Frankfurt first — never split the two.
- **Store energy as (value, anchor, period_ms) and settle lazily inside a locking PL/pgSQL function; never sweep with a cron**
  - Rejected: A background ticker that credits energy/tax to all players on a schedule
  - Why: A sweeper is O(players) per tick, cannot scale, and is wrong the moment it lags. Lazy settlement is O(1) per request and exactly correct at any polling frequency. Crucially, advancing the anchor by exactly gained×period (not to now) preserves the sub-tick remainder, so a client polling every 10 s with a 60 s regen period still regenerates correctly.
- **Encode the regen rate as a PERIOD in integer milliseconds-per-unit, not a rate in units-per-second**
  - Rejected: Floating-point units per second, or a fractional-remainder column
  - Why: Integer division gives exact arithmetic with zero drift and no extra column: gained = elapsed_ms / period_ms, new_anchor = anchor + gained × period_ms. With a fractional rate you must carry a remainder or silently lose progress on every read.
- **On any rate change, settle with the OLD rate first, then write the NEW rate, carrying the partial tick proportionally (new_anchor = now − remaining × new_period / old_period)**
  - Rejected: Snapping the anchor to now on rate change
  - Why: Settling first splits the interval at an exact tick boundary so no time is double-counted or lost. Snapping would silently discard up to one full tick of progress on every upgrade purchase — always in the house's favour, and players notice.
- **Migrate rates lazily via players.rate_config_ver rather than sweeping all players on config publish**
  - Rejected: A migration job that recomputes and rewrites every player row when a balance patch ships
  - Why: Because settle already advanced the anchor to a point consistent with the old rate, applying the new rate at the player's next request is exactly correct. Publishing a balance patch becomes an O(1) pointer swap instead of an O(players) write storm on Neon.
- **chi v5.3.2 over Go 1.22+ net/http.ServeMux**
  - Rejected: stdlib ServeMux (and echo/gin)
  - Why: ServeMux has no middleware primitive, no route groups, and no RoutePattern(). We need four distinct middleware profiles (auth/game/admin/public) and low-cardinality route labels for Prometheus and per-route rate limits — with stdlib you reimplement chi badly and maintain a parallel route map that drifts. echo/gin were rejected for infecting every function with custom Context types for zero benefit.
- **pgx v5.10.0 + sqlc v1.31.1, no ORM**
  - Rejected: GORM / bun / ent
  - Why: The hard parts here are exactly what an ORM hides: multi-CTE data-modifying statements, FOR UPDATE lock ordering, ON CONFLICT ... RETURNING, unnest() array params, PG18 RETURNING OLD/NEW. Any ORM would push 100% of that into raw SQL, so you pay reflection and N+1 hazards for nothing. sqlc parses the real schema, so a wrong column is a compile error.
- **Use pgx default_query_exec_mode=cache_statement on Neon's pooled endpoint, with an env escape hatch**
  - Rejected: QueryExecModeExec / simple_protocol, the usual 'PgBouncer breaks prepared statements' advice
  - Why: Verified: Neon runs PgBouncer with max_prepared_statements=1000, and PgBouncer ≥1.22 rewrites protocol-level prepared statements onto internal names. cache_statement therefore works and gives server-side plan caching. The DB_QUERY_EXEC_MODE env var lets us fall back to describe_exec in 90 seconds if Neon ever changes that config (watch for SQLSTATE 26000).
- **Run two pgx pools: pooled endpoint for all request traffic, direct endpoint for migrations and session-state work**
  - Rejected: A single pool against either endpoint
  - Why: The pooled endpoint forbids session-level SET, LISTEN/NOTIFY, session advisory locks, SQL-level PREPARE, and WITH HOLD cursors. goose's session locker needs session advisory locks. Splitting the pools makes the constraint explicit and enforceable, and a CI job that runs the DB tests through a real PgBouncer in transaction mode catches violations before production.
- **Set statement_timeout/lock_timeout/idle_in_transaction_session_timeout via ALTER ROLE, plus SET LOCAL inside transactions**
  - Rejected: Session-level SET on connect, or RuntimeParams in the pgx config
  - Why: You cannot SET per session through PgBouncer in transaction mode, and unlisted startup RuntimeParams can be rejected or leak across tenants. Role-level defaults are inherited by every backend regardless of pooling, and SET LOCAL is transaction-scoped and therefore pooler-safe. lock_timeout=3s converts a hot-row pile-up into a clean 503 instead of a hang.
- **READ COMMITTED with pessimistic SELECT ... FOR UPDATE row locks**
  - Rejected: SERIALIZABLE isolation, or an optimistic version-column CAS retry loop
  - Why: Contention here is self-contention on one player's row (a double-tapped Collect button). SERIALIZABLE would turn that into 40001 retry storms with unbounded latency; a CAS loop wastes N transactions where a lock costs one wait. Optimistic concurrency is used exactly once — consuming a kingdom invite — where the object is naturally single-shot.
- **Lock multiple players in ascending UUID order using separate statements, never ORDER BY ... FOR UPDATE**
  - Rejected: SELECT ... WHERE id = ANY($1) ORDER BY id FOR UPDATE
  - Why: Postgres acquires row locks during the scan and the planner may choose a scan order that differs from the ORDER BY, so that form can still deadlock. Two separate locking statements in Go-sorted order make A-attacks-B and B-attacks-A serialize on min(A,B) and eliminate deadlock structurally.
- **Idempotency via insert-first ON CONFLICT DO NOTHING RETURNING, with a SAVEPOINT so business errors are committed and infrastructure errors roll back**
  - Rejected: SELECT-then-INSERT, or storing idempotency records in Redis
  - Why: Check-then-act is a race even under READ COMMITTED: both workers see 'absent', both insert, the loser may already have executed side effects. Committing the response in the same transaction as the state change makes replay exactly consistent. Rolling back infrastructure failures (including the key) is what makes the deadlock-retry wrapper safe.
- **FOR UPDATE NOWAIT on a contended idempotency key, returning 409 request_in_flight**
  - Rejected: Blocking until the in-flight transaction commits
  - Why: A blocking wait holds a mobile retry hostage for up to statement_timeout. Fail fast and let the client's exponential backoff handle it — this is Stripe's behaviour and it keeps p99 bounded.
- **ChaCha8 from math/rand/v2, seeded by HMAC-SHA256 over server secrets**
  - Rejected: PCG (rand.NewPCG)
  - Why: PCG accepts only 128 bits of seed, discarding half our digest, and its state is small enough that a player observing a handful of outputs could recover it and predict future recruit tiers. Shop windows are publicly predictable in time, so this is a live concern. ChaCha8 takes the full 32-byte seed, leaks nothing about state, and costs ~1 ns/word.
- **Derive shop rolls purely from (player_id, 5-minute window, reroll_counter); derive recruits from a transaction-incremented recruit_seq**
  - Rejected: Rolling the shop at request time and persisting the result, or seeding from request data
  - Why: A derived shop is bit-identical on every retry, so there is literally nothing to reroll, and GET /v1/shop costs ZERO database writes — significant, since it is the most-polled endpoint in the game. Recruit outcomes are bound to a counter consumed atomically inside the transaction, so a force-quit cannot dodge a bad tier.
- **Stateless HMAC-signed PvP target offers**
  - Rejected: A pvp_offers table with rows written per target refresh
  - Why: Writing 3 rows per refresh is ~6M rows/day of pure churn at 100k DAU. The offer only needs to prove 'the server offered you this target recently' (preventing target-shopping for the richest player); everything that matters — shield, energy, kingdom, cooldown — is re-validated under lock at attack time anyway.
- **Enforce the 30-minute shield as a timestamp compared on read (shield_until), never as an expiring row**
  - Rejected: A shields table with a cron that deletes expired rows
  - Why: A past timestamp compares false, so expiry is free and instantaneous. The same trick handles newbie protection and shop windows. Generalised: an expiring state is a timestamp compared on read, never a row that must be swept.
- **No WebSockets in v1**
  - Rejected: A WebSocket layer for live state push
  - Why: Nothing in the game is synchronous, and lazy accrual means the client can render a perfectly accurate ticking energy counter locally from (current, period_ms, anchor_at, server_time_ms) with zero traffic. Config changes propagate via the X-Config-Version header already on every response. A socket layer would add connection state to a stateless binary and force blue/green deploys to drain long-lived connections.
- **No Redis in v1**
  - Rejected: Redis for sessions, rate limiting, and leaderboards
  - Why: Every candidate use has a better single-node answer: refresh tokens in Postgres (revocation must be real), in-process x/time/rate + LRU for limits, an index scan for leaderboards, atomic.Pointer for the config cache, and a derived shop that stores nothing. Adopt Redis the day a second app container exists — that is the explicit trigger.
- **goose v3.28.0 against the direct endpoint**
  - Rejected: golang-migrate, or Atlas
  - Why: goose keeps up/down in one file, supports Go migrations in the same version sequence (needed for data backfills like recomputing players.power), and has NO TRANSACTION for CREATE INDEX CONCURRENTLY. Atlas's best half is a paid cloud product and adds a non-Go binary to CI. goose's session locker needs session advisory locks — hence the direct endpoint.
- **All currency is int64 with integer basis-point multipliers and floor rounding; no float64 ever touches the economy**
  - Rejected: float64 multipliers, or NUMERIC
  - Why: Integer basis points make server, admin simulator and client-side display prediction bit-identical, and make SUM(ledger.delta) == players.gold reconcile exactly. Any float in this path guarantees a slow accounting drift that is nearly impossible to debug after the fact.
- **Serialise any value that can exceed 2^53 (gold, xp, power, prices) as a JSON string**
  - Rejected: Plain JSON numbers throughout
  - Why: GDScript's JSON parser is float-backed for large values, so a late-game gold balance would silently lose precision on the client. Small bounded integers (level, energy, counts) stay as numbers.
- **Keep internal/game strictly pure — no context, no pgx, no net/http, no time.Now() — enforced by a CI dependency check**
  - Rejected: Services that read the DB inline while computing rewards
  - Why: This one boundary is what makes the economy unit-testable with zero infrastructure, makes the 30-day balance simulator possible, and makes every shop/recruit/battle roll reproducible for audit. It is the highest-leverage structural rule in the design.
- **Restrict continuous-rate effects (energy regen, tax rate) to player-controlled sources; kingdom upgrades affect only discrete-event multipliers**
  - Rejected: Kingdom upgrades that boost the passive tax rate
  - Why: A kingdom upgrade that changed the tax rate would require settling up to 50 members atomically on purchase. Confining rate effects to family upgrades and stat points removes that entire class of complexity. (Owner question — the fallback is a bounded pgx.Batch settle in ascending player_id order.)
- **Kingdom reputation accumulates on kingdom_members.reputation_contributed and is rolled up every 60 s**
  - Rejected: UPDATE kingdoms SET reputation = reputation + x on every member attack
  - Why: That would serialize every active member of a kingdom behind one hot row. Each member updates only their own row (which the transaction already holds), and a background roll-up maintains the denormalised total for the leaderboard.
- **No request signing; ship an X-Client-Version kill switch now and Apple App Attest at v1.1**
  - Rejected: HMAC request signing with a key embedded in the Godot client
  - Why: The signing key ships inside the .pck and is extractable in minutes with gdsdecomp — it buys hours against one determined attacker for permanent engineering and debuggability cost. The real defence is that the server owns every number. App Attest is hardware-backed and free, and is the only client-integrity mechanism with actual teeth.
- **Anti-cheat centred on an append-only ledger plus a faucet-ceiling anomaly check**
  - Rejected: Heuristic behavioural detection alone
  - Why: Energy is the only input to collect gold and the server owns regeneration, so max honest income over any window is a closed-form function. Anything above it is deterministically an exploit or a bug — no false positives. Backed by SUM(ledger.delta) == players.gold, which catches every accounting bug including untested ones.
- **Ed25519 JWT access tokens (15 min) + opaque rotating refresh tokens in Postgres with family reuse-detection**
  - Rejected: Opaque access tokens looked up per request, or stateless refresh JWTs
  - Why: JWT access avoids a DB round trip on every request (~20% of p50 at this latency), and Ed25519 lets the Next.js admin verify with only the public key. Refresh must be revocable for real — a stateless 60-day refresh JWT on a stolen device cannot be revoked. Reuse detection revokes the whole family on replay.
- **Anonymous device accounts keyed on sha256(device_secret) stored in the iOS Keychain, with a 24 h newbie shield and hard per-/24 signup limits**
  - Rejected: An RSA device keypair with challenge-response, or immediate Sign in with Apple
  - Why: Godot 4 has no Ed25519 and RSA-2048 keygen costs ~1 s on first launch, while the private key would live in the same Keychain as the secret — identical threat model. Zero-friction onboarding matters more. The newbie shield plus signup rate limits is what actually kills alt-farming, which is the dominant exploit in a 3%-steal PvP game.
- **On Apple/Google link conflict, return 409 with both profile summaries and let the player choose which account to keep**
  - Rejected: Automatic account merging
  - Why: Merging two inventories, soldier rosters and kingdom memberships is a bug factory with no correct answer. 'Keep one' is what every comparable game ships and it is implementable in a day.
- **Versioned config bundle in Postgres, served pre-gzipped from an atomic.Pointer with ETag/304, polled every 30 s**
  - Rejected: LISTEN/NOTIFY for config invalidation, or config files in the image
  - Why: LISTEN/NOTIFY is forbidden on the pooled endpoint; a 30 s poll is one trivial indexed query and far simpler. Pre-gzipping once per version makes serving a memcopy. Never reject a stale client — execute at server prices and set X-Config-Stale, or every balance publish breaks every in-flight player.
- **Distroless static-debian12:nonroot on a CGO_ENABLED=0 amd64 binary, built in CI**
  - Rejected: alpine, or scratch
  - Why: alpine brings musl DNS quirks under load and a shell for an attacker; scratch has no CA bundle, so Apple JWKS verification fails at runtime with a confusing error. distroless/static ships CA certs, runs as UID 65532, and lands at ~25 MB. Building in CI avoids arm64→amd64 QEMU drift from the Mac.
- **Caddy 2.11.4 blue/green with a graceful config reload, and /readyz flipping to 503 three seconds before shutdown**
  - Rejected: Traefik label-driven routing, or nginx + certbot
  - Why: Caddy gives automatic ACME in three lines, graceful reload (in-flight requests finish), and HTTP/3. The /readyz-before-/healthz distinction is what eliminates the ~1 s of 502s that naive blue/green produces — most implementations miss it.
- **SOPS + age encrypted secrets committed to the repo, decrypted only on the VPS**
  - Rejected: GitHub Actions secrets echoed over SSH into .env
  - Why: CI then needs only an SSH deploy key and a GHCR token — nothing that can decrypt production. Every secret rotation becomes a reviewable, auditable commit instead of an untracked click in a web UI.
- **Integration tests against real Postgres 18 using a template database, plus a second CI pass through PgBouncer in transaction mode**
  - Rejected: sqlmock, SQLite, or re-running migrations per test
  - Why: The design depends on FOR UPDATE semantics, CTE execution rules and PL/pgSQL — a mock tests nothing. CREATE DATABASE ... TEMPLATE costs ~30 ms per test versus seconds for a migration run. The PgBouncer pass catches accidental session SET, LISTEN, or advisory-lock usage before production rather than at 2 a.m. after launch.
- **Make time an explicit parameter everywhere: app.settle_player(id, ts) and a Clock interface in services**
  - Rejected: Calling now() implicitly inside game SQL and time.Now() in services
  - Why: It makes a 30-day economy simulation run in milliseconds and makes the concurrency tests deterministic. Combined with a GREATEST monotonicity guard in settle, it also makes the system robust to VPS/Neon clock skew.

## Risks flagged

- Neon could change its PgBouncer configuration (e.g. drop max_prepared_statements below 1), which would break pgx's cache_statement mode with SQLSTATE 26000 'prepared statement does not exist' on every query. Mitigation: the DB_QUERY_EXEC_MODE env escape hatch, a startup self-test across three pooled connections, and an alert on 26000. Recovery is a 90-second redeploy, but it will be a confusing outage if nobody has read this section first.
- app.settle_player is PL/pgSQL, which splits mechanism between Go and SQL. If someone later adds a code path that mutates players.gold or energy WITHOUT calling settle first, accrual silently stops or double-credits for that path. Mitigation: make every service method go through settleAndSync(), and add a CI grep that flags any UPDATE players touching energy_* or tax_* outside db/migrations. This is the most likely long-term source of a subtle economy bug.
- Cross-region latency is the dominant performance risk. If the owner deploys to Hetzner Falkenstein against Neon eu-west-2 anyway, every mutating request pays ~50 ms of pure network and the game will feel sluggish on the Collect tab specifically, where players tap repeatedly. This is not fixable in code.
- Neon's scale-to-zero (5-minute idle suspend) will cause several-hundred-millisecond cold starts during low-traffic hours, appearing as random timeouts to early players. Disable it on the production branch — but that changes the billing model from pay-per-use to always-on, which the owner should be told about before the first invoice.
- int64 gold caps at ~9.2e18. Idle games are notorious for exceeding int64 within a year if the upgrade curve is exponential. If the balance ends up multiplicative rather than additive, a migration to a {mantissa, exponent} representation touches the ledger, every CHECK constraint, and the client. Decide the shape of the late-game curve before launch, not after.
- The RNG reproducibility contract is fragile in a specific way: adding or reordering a single r.Uint64() call, or iterating a Go map to build a weight table or template pool, silently changes every shop and every recruit. Golden tests catch it in CI, but only if nobody blesses a golden diff without bumping RNGVersion. Make that a written review rule.
- PvP at launch will have too few real players for a fair power band, producing empty target lists or grossly mismatched fights. The bot-seeding plan (~2000 synthetic players) must actually ship in milestone 9, not be deferred — an Attack tab that returns 'no targets' on day one kills the core loop.
- The 3%-steal mechanic plus zero-friction anonymous signup is a standing invitation to alt-farming: create accounts, feed them gold, farm them. The 24-hour newbie shield, level-5 gate, per-/24 signup limits and the pair cooldown together should cover it, but this is the exploit most likely to be found first and it will need tuning within days of launch. Instrument game_attacks_total by defender age from day one.
- Kingdom reputation roll-up runs every 60 s in-process. If the process dies mid-roll-up, kingdoms.reputation can lag members' contributions. It is eventually consistent by construction (the roll-up is a full SUM, not an increment), but leaderboard positions will visibly jitter after a deploy. Acceptable, but expect a support question.
- Single VPS means a single point of failure with no automatic failover. A DigitalOcean host incident takes the game down entirely until someone manually restores. Acceptable for launch given Neon holds all state and the app is stateless, but write and rehearse the 'restore on a fresh droplet' runbook before you need it — target under 20 minutes.
- The idempotency key table grows at roughly one row per mutating action. At 100k DAU with 50 actions/day that is 5M rows/day; the 48-hour GC must actually run and must be batched, or the DELETE will lock-contend with live traffic and the table will bloat. Verify the GC in staging under realistic volume.
- No load testing before launch. The pool sizing (20 connections), rate limits, and the matchmaking query's behaviour at scale are all reasoned rather than measured. The metrics are in place to catch problems, but a marketing spike could find the ceiling before you do. A k6 run against a Neon staging branch the week before launch is cheap insurance.

## Questions raised for the owner

- Do kingdom upgrades need to boost the passive TAX rate, or is it acceptable for them to boost only discrete-event rewards (collect gold, XP, attack loot, shop discounts)? Restricting them to discrete events removes an entire class of concurrency complexity — a kingdom upgrade purchase would otherwise have to atomically settle every member. If tax must be boosted, say so now; the fallback (a batched settle of up to 50 members) is implementable but doubles the cost of that feature and adds a deadlock surface.
- Tier colours: epic and mystic are both specified as purple. Which resolution do you want? My recommendation is to keep epic = purple (#8B5CF6) and move mystic to cyan/teal (#22D3EE) for maximum separation from legendary-yellow and special-red. The alternative is epic = deep indigo (#6366F1) with mystic staying purple. Colours live in the config bundle so this is changeable later without a client update, but item art will be generated against whatever we choose, so decide before the asset run.
- What is the intended shape of the late-game gold curve — roughly additive (a level-60 player earns maybe 100–1000× a level-1 player) or exponential/idle-style (10^12× and climbing)? This determines whether int64 gold is safe forever or whether we need a {mantissa, exponent} representation from day one. Retrofitting it later touches the ledger, every constraint, and the client.
- Should the passive tax be auto-credited to gold, or should it sit in a 'pending' pile that the player taps to collect? If Hetzner is required on cost, I would move the Neon project to eu-central-1 Frankfurt before any data exists — which is now, while the database is still empty. # Adversarial review — verdict: needs-revision


## BLOCKER (3)

### §6.4 — the flagship "single-statement atomic collect" cannot work. `app.settle_player` performs an `UPDATE players` and the same top-level statement's `upd` CTE performs a second `UPDATE players` on the *same row*.

**Breaks because:** PostgreSQL docs (queries-with.html): "All the statements are executed with the same snapshot, so they cannot 'see' one another's effects on the target tables" and "Trying to update the same row twice in a single statement is not supported." settle_player's UPDATE runs inside a VOLATILE plpgsql function during execution of the outer statement, so its new tuple version has cmin > the outer statement's snapshot curcid and is invisible to the outer UPDATE; the outer UPDATE scans the pre-settle tuple, then heap_update returns TM_SelfModified with tmfd.cmax != estate->es_output_cid. Result: `ERROR: tuple to be updated was already modified by an operation triggered by the current command` on every single collect. The pgsql-hackers thread on that error confirms it arises "by a command in a volatile function used in the query", not only from BEFORE triggers. In the event a plan shape avoids the error, the alternative is worse and silent: the outer UPDATE builds its new tuple from the pre-settle version, so energy_anchor_at, tax_pending_micro, tax_anchor_at and settled_at written by settle are all reverted — energy and tax accrual reset on every collect. The design explicitly calls this query "the template every other mutating action copies", so the defect propagates to shop/buy, recruit, upgrade and tax/claim.

**Fix:** Move the whole action into a plpgsql function `app.collect(p_id, p_now, p_job_id, p_times, …)`. Inside plpgsql each statement gets a CommandCounterIncrement, so statement N+1 sees statement N's writes — exactly the property a single SQL statement does not have — and it still costs ONE network round trip. Shape: (1) `r := app.settle_player(p_id, p_now);` (2) `IF r.energy_current < p_energy_cost*p_times THEN RAISE EXCEPTION 'insufficient_energy' USING ERRCODE='P0001';` (3) `INSERT INTO player_job_stats … ON CONFLICT DO UPDATE … RETURNING collects INTO new_collects;` (4) compute gold via `SELECT COALESCE(SUM(...),0) INTO g_gold FROM generate_series(1,p_times) g(i)` — pure, touches no table; (5) `SELECT count(*) INTO new_level FROM unnest(p_level_xp) t WHERE t <= r.xp + g_xp;` (6) `UPDATE players … WHERE id = p_id RETURNING p.* INTO r;` — now sees the settled row; (7) `INSERT INTO ledger … VALUES (…gold…),(…xp…);` (8) `RETURN`. The RAISE in step 2 rolls back to the §6.2 SAVEPOINT, which is exactly the semantics §6.2 already requires. Apply the identical restructure to every other mutating action, and write the rule into the repo: NEVER call app.settle_player from a statement that also writes `players`.

### §8.1 — the 30-minute protection shield is granted to the wrong player. `ShieldUntil: nullTime(!res.AttackerWins, now.Add(cfg.PvP.ShieldDuration))` sets the shield when `!AttackerWins`, i.e. when the defender WON.

**Breaks because:** The brief says "A defender who LOSES gets a 30-minute protection shield", and the design's own §8.3 says "Set: only when the *defender loses*". As coded the semantics invert: a defender who repels an attack becomes un-attackable for 30 minutes and disappears from everyone's matchmaking band, while a defender who just lost 3% of their gold gets no protection and stays in the pool. Since gold is conserved and the pair cooldown only restrains a single attacker, a weak-defence player is farmed by an unbounded number of distinct attackers with no shield ever triggering — 0.97^n decay of their whole balance. This is the most player-visible failure the design could ship.

**Fix:** `ShieldUntil: nullTime(res.AttackerWins, now.Add(cfg.PvP.ShieldDuration))`. Add to milestone 9's gate: `TestShieldGrantedOnlyToLosingDefender` — with a stubbed `battle.Resolve`, force a win and a loss and assert `defender.shield_until > now` iff `res.AttackerWins`, `attacker.shield_until` untouched in both cases, and that a shielded player is absent from `FindAttackTargets`.

### §3 — `ALTER ROLE emperors_app SET statement_timeout='8s'` / `lock_timeout='3s'` also applies to schema migrations, which run as the same role.

**Breaks because:** Migrations run via `cmd/api --migrate-only` against the direct endpoint using the same `emperors_app` role, so they inherit the role-level defaults. Any migration statement over 8 s dies with 57014 mid-deploy: an index build on a grown `items`/`ledger`/`battles`, any backfill, and specifically the Go data migrations goose was chosen for ("recomputing players.power after an items change"). `lock_timeout=3s` additionally kills any ALTER TABLE that has to queue behind a live query — and it will, because deploy.sh runs migrations (step 1) while the old colour is still serving traffic (step 4 stops it). The failure lands mid-deploy with the schema half-applied and expand/contract broken.

**Fix:** `CREATE ROLE emperors_migrate LOGIN; GRANT emperors_app TO emperors_migrate;` with its timeouts unset (or `statement_timeout=0`, `lock_timeout='30s'`). Point the migration path at that role, keep `DATABASE_URL` on `emperors_app`. Own the ledger tables with `emperors_migrate` too — that also turns `REVOKE UPDATE, DELETE ON ledger FROM emperors_app` into a real control rather than a speed bump the owner can re-grant — and apply the same GRANT/REVOKE pair in the monthly partition-creation job so new partitions inherit it.


## MAJOR (15)

### §14 — the in-process scheduler's `pg_advisory_xact_lock(hashtext($job))` does not prevent double execution during blue/green overlap; it is a *blocking* lock.

**Breaks because:** The stated purpose is "so overlapping blue/green containers can't double-run". A blocking advisory lock makes the second container wait, acquire the lock the instant the first commits, and then run the job a second time — the exact outcome it was meant to prevent. During the 30-second overlap in deploy.sh this hits the anomaly scan, the leaderboard snapshot, the kingdom reputation roll-up and the ledger partition creation. And `lock_timeout=3s` applies here too, so in practice the second container aborts with 55P03 and the job is logged as a failure rather than a skip.

**Fix:** Use `pg_try_advisory_xact_lock(hashtext($1))` and return silently when false — never log that as an error. Because a try-lock still permits an immediate re-run after the first finishes, add a debounce inside the same transaction: `CREATE TABLE job_runs (job text PRIMARY KEY, last_started_at timestamptz NOT NULL, last_finished_at timestamptz);` then `SELECT 1 FROM job_runs WHERE job=$1 AND last_started_at > now() - $2::interval` with $2 = 0.8 × cadence; skip if a row comes back, otherwise upsert `last_started_at` and run.

### §14 — Grafana Alloy cannot reach the metrics endpoint. The API binds Prometheus to `127.0.0.1:9090` inside its own container while Alloy runs with `network_mode: host`.

**Breaks because:** `127.0.0.1:9090` inside a bridge-networked container is that container's loopback, not the host's. A host-namespace Alloy resolves `127.0.0.1:9090` to the VPS loopback, where nothing listens — the compose file publishes no port for the api services (`expose: ["8080"]` only). Every scrape fails, so all of §13 — including `game_gold_minted_total`, called "the single most valuable dashboard in the project" — produces no data. Blue/green compounds it: two containers would contend for one port. Separately, Alloy mounts `./alloy.river` at `/etc/alloy/config.river`, but the grafana/alloy image's default command is `run /etc/alloy/config.alloy`; the file is never read.

**Fix:** Bind metrics to `0.0.0.0:9090` inside the container (still unreachable from the internet — no published port, and Caddy never proxies it). Drop `network_mode: host` and put Alloy on the compose network. Rename the config `alloy.alloy`, mount at `/etc/alloy/config.alloy`. Scrape both colours with a label: `prometheus.scrape` targets `[{__address__="api-blue:9090", colour="blue"}, {__address__="api-green:9090", colour="green"}]`. Verify at milestone 1 by asserting a non-empty `up` series before any game code exists.

### §2 vs §6.2 — idempotency is specified both as a chi middleware (`r.Use(mw.Idempotency(idemStore))`) and as statements that must run inside the service's transaction. Those are mutually exclusive.

**Breaks because:** §6.2's correctness argument depends on the claim INSERT, the SAVEPOINT, the use-case and the stored response all committing in ONE transaction, and on an infrastructure failure rolling back the claim so the `InTx` retry is safe. A chi middleware runs before and after the handler and has no access to the `pgx.Tx` the service opens inside `InTx`. If it uses its own transaction, the claim commits independently of the state change — producing exactly the bug the section exists to prevent: a crash between claim-commit and action-commit leaves a poisoned key that replays a response for work that never happened. If instead the middleware owns the transaction, it is no longer a middleware and the `Recover`/`Timeout` ordering around it becomes wrong.

**Fix:** Split it. A thin middleware only (a) rejects mutating routes with no `Idempotency-Key`, (b) validates length 16–64, (c) computes `sha256(method|RoutePattern|canonical-body)` and stashes both in the request context — zero DB access. The protocol moves into `internal/service`: `WithIdempotency[T any](ctx, tx pgx.Tx, playerID uuid.UUID, key string, hash []byte, endpoint string, fn func(pgx.Tx) (T, int, error)) (T, int, bool, error)`, called as the first thing inside the `InTx` closure, doing the ON CONFLICT DO NOTHING RETURNING claim, `tx.Begin()` for the savepoint, the fn call, `ROLLBACK TO SAVEPOINT` on business error, and the status=1 UPDATE. Handlers stay 15 lines; the transaction stays one.

### §8.2 — stateless HMAC offers do not deliver the security property claimed for them. The design says the offer "prevents target-shopping (scanning for the richest player)"; it does not.

**Breaks because:** `GET /v1/attack/targets` is by design free ("Zero database writes"), refreshable via `?refresh=bool`, rate-limited at 30/min, and returns a `gold_band` per candidate. A scripted client pulls 30 requests/minute × 3 offers = 90 signed offers per minute, sorts by gold band, and attacks only the fattest — which is target-shopping, and it is *cheaper* here than in the `pvp_offers`-table design that was rejected. The HMAC proves the server offered the target; it does not bound how many targets the server will offer. The design's anomaly detector has no check for it either — the faucet ceiling is scoped to `reason='collect'`.

**Fix:** Make the target set a pure function of time, exactly like the shop — the design already owns this pattern and its anti-reroll proof. Derive the candidate set from `seed = HMAC(pvp_offer_key, player_id || floor(unix/300) || refresh_counter)`, use it for the random pivot in `FindAttackTargets`, and put `window_id` and `refresh_counter` inside the signed payload. A plain re-GET in the same window then returns a bit-identical set (nothing to shop), and an explicit refresh increments `players.pvp_refresh_counter` in a transaction that charges diamonds — turning the exploit into a monetization surface. Also drop `gold` from the payload for v1, or bucket it so coarsely (`"<10k"`, `"10k–100k"`, `"100k+"`) that sorting is unprofitable. Add anomaly check (7): players whose attacked-defender gold percentile is consistently >p90.

### §10/§17 — kingdom upgrades cannot be paid for. `kingdoms.gold_bank` exists and `POST /v1/kingdoms/{id}/upgrades/{key}/buy` exists, but nothing ever puts gold into the bank: no deposit endpoint, no ledger reason, no rule about whether the leader pays personally.

**Breaks because:** `gold_bank` defaults to 0 and no code path increments it, so every kingdom upgrade purchase fails its affordability check forever. The kingdom upgrade tree is an explicit brief requirement ("The kingdom has its own upgrade tree … that benefits all members") and milestone 10 is gated on "six tabs complete" — which is not achievable as specified.

**Fix:** Add `POST /v1/kingdoms/{id}/donate {amount}` (idempotency-key required). One transaction: settle+lock the donor, guard `gold >= amount`, debit the player, `UPDATE kingdoms SET gold_bank = gold_bank + amount`, `UPDATE kingdom_members SET gold_donated = gold_donated + amount`, and write a `kingdom_donate` ledger row for the player plus a row in a separate `kingdom_ledger` table — keeping `SUM(ledger.delta)==players.gold` exactly true. Extend the global lock-ordering rule with a tier below `players` for `kingdoms` so donate and upgrade-purchase cannot deadlock. Guard the purchase with `UPDATE kingdoms SET gold_bank = gold_bank - cost WHERE id=$1 AND gold_bank >= cost RETURNING *` (0 rows → 402).

### §8.1/§17 — kingdom reputation is never written, so the kingdom leaderboard is permanently zero. The Go code passes `Reputation: res.ReputationGain` into `PvPCreditAttacker`, but that query declares no such parameter and updates no reputation column; `players` has no reputation column; and nothing writes `kingdom_members.reputation_contributed`, which the 60-second roll-up sums.

**Breaks because:** This is a compile-time mismatch with sqlc — the generated `PvPCreditAttackerParams` will have no `Reputation` field, so `internal/service/pvp.go` will not build — and once someone 'fixes' it by deleting the field, a silent permanent zero: `SUM(kingdom_members.reputation_contributed)` is always 0, `kingdoms.reputation` is always 0, `GET /v1/leaderboards/kingdom_reputation` is a flat board. The brief is explicit: "Every member attack earns the kingdom 'reputation', which drives a kingdom leaderboard." Separately, the ledger declares `currency='reputation'` with no balance column anywhere for the reconciler to compare against, so that currency silently escapes the design's headline invariant.

**Fix:** In the attack transaction, after the credit: `UPDATE kingdom_members SET reputation_contributed = reputation_contributed + $2 WHERE player_id = $1` (guarded on `attacker.KingdomID.Valid`; 0 rows for a kingdom-less attacker is fine). Remove `Reputation` from `PvPCreditAttackerParams`. Then either make `kingdom_members.reputation_contributed` the reconciliation target for `currency='reputation'` in the nightly reconciler and in `TestLedgerReconciles`, or drop 'reputation' from the ledger currency enum and journal it only in `battles` — but do not leave a ledger currency with no balance to reconcile, because that quietly weakens the test the design calls "the single most valuable test in the codebase".

### §5.6 — the design proposes a game-design change that contradicts the brief, in order to solve a problem it has already solved elsewhere in the same document.

**Breaks because:** The brief states: "Family and Kingdom upgrades boost BOTH collect income and tax." §5.6 recommends forbidding kingdom upgrades from touching any continuous rate, with a `pgx.Batch` settle of up to 50 member rows as the fallback. Both options are bad and neither is needed. The batch fallback holds 50 `players` row locks in one transaction, so every one of those members' concurrent requests hits `lock_timeout=3s` and 503s — a kingdom leader buying an upgrade briefly 503s their whole kingdom. Meanwhile §5.5 already contains the correct mechanism: lazy rate migration keyed on a version integer, invented for config publication and then not generalized.

**Fix:** Add `kingdoms.rates_ver int NOT NULL DEFAULT 0` and `players.rate_kingdom_ver int NOT NULL DEFAULT 0`. On a rate-affecting kingdom upgrade purchase, bump `kingdoms.rates_ver` — one row, one lock, O(1). Extend the `settleAndSync` fast-path check from `row.RateConfigVer == cfg.Version` to `row.RateConfigVer == cfg.Version && row.RateKingdomVer == kingdomRatesVer` (cache the kingdom's `rates_ver` in-process on the same 30 s tick as the config bundle). On mismatch, take the slow path that already exists: settle with old rates, then `apply_rates` with newly derived ones. Reset `players.rate_kingdom_ver = 0` on join/leave. This keeps the brief intact, causes no settle storm, and reuses code milestone 3 already ships and tests.

### §10/§12 — the sample economy numbers invert the brief's hybrid model: passive tax income is roughly 12–60× active collect income.

**Breaks because:** The brief specifies collect as "the primary gold source" with "a small passive 'tax' income". Using the design's own /v1/state sample at level 27: `tax.rate_gold_per_hour = 900`, `cap_gold = 7200` (8 h × 900), so a player opening the app three times a day harvests ~21,600 gold/day passively. Energy is `max 60` at `period_ms 45000`; a player draining a full bar three times a day spends 180 energy/day, which at the brief's 2 gold/energy is 360 gold/day and even at an aggressive late-game 10 gold/energy is 1,800 gold/day. Passive dominates active by 12× to 60×. The Collect tab — the game's primary loop, and the tab the design optimizes hardest for (batching, milestones, single-statement writes) — becomes economically irrelevant, and the +5/10/15% milestone bonuses never matter. Nothing in the validator or the simulator asserts the ratio, so this ships silently.

**Fix:** Enforce the ratio as a publish gate. Define `active_gold_per_day = (86400000/energy_period_ms + energy_max) * best_unlocked_gold_per_energy` and require `tax_gold_per_day <= 0.25 * active_gold_per_day` for every level bracket in the config, as a hard assertion in the §12 validator alongside the existing curve checks. For the sample player that means tax of roughly 20–60 gold/hour (cap 160–480 over 8 h), or raising gold-per-energy ~15×. Make `cmd/simulate` print the active:passive split per week as a first-class output and surface it on `/admin/config/{id}/simulate` — this is precisely the regression that preview exists to catch.

### §12 — the config validator has no mint-side invariants, so the two obvious gold-printing loops in the specified API surface are unguarded.

**Breaks because:** Anti-cheat rests on "the server owns every number" plus a faucet ceiling scoped to `reason='collect'`. Neither catches an economy that mints by construction. (1) `POST /v1/inventory/sell` yields gold and `POST /v1/shop/buy` costs `cfg.Shop.PriceFor(rarity, kind)` — if sell value exceeds buy price for any single (rarity, kind) pair, a script farms that pair forever. (2) `POST /v1/soldiers/{id}/dismiss` returns `gold_refund` while recruit charges a price fixed by *type* against a *randomly rolled* rarity — if refund scales with the rolled rarity, recruiting peasants and dismissing every above-average roll is positive-EV, legal, invisible to the collect faucet ceiling, and indistinguishable from normal play in the action-rate check.

**Fix:** Add publish-blocking assertions to the §12 validator: (a) `for all (rarity, kind): sell_value(rarity,kind) < shop_price(rarity,kind)`, with sell value a function of rarity/kind ONLY — never of `roll_bp`, or the high-roll tail reopens the loop; (b) `for all soldier_type t: dismiss_refund(t) < recruit_price(t)`, with refund a function of TYPE only, never of rolled rarity. Add `game_gold_minted_total{reason="sell"}` and `{reason="dismiss"}` with an alert if either exceeds 20% of `{reason="collect"}` over a rolling hour.

### §8.2/§13 — bot gold is an unbounded inflation faucet, and the design explicitly excludes it from the one dashboard that would detect it.

**Breaks because:** Bots hold synthetic gold that "regenerates on a schedule" (daily top-up job, §14). Real players steal 3% per attack and that gold enters the real economy permanently. With ~2000 bots across the power curve plus a daily top-up, the faucet is sized by the top-up job rather than by any designed budget. The design then says bot gold is "excluded from economy dashboards" — meaning `game_gold_minted_total`, described as "the single most valuable dashboard in the project", is blind to the largest early-game faucet in the game. The §7.5 faucet ceiling covers only `reason='collect'`, so nothing catches it there either.

**Fix:** Meter it: emit `game_gold_minted_total{reason="bot_topup"}` from the top-up job and INCLUDE it on the faucet dashboard, labelled so it can be split out but never hidden. Give the job a hard global daily budget from the config bundle (`economy.bot_gold_daily_budget`) and distribute that budget across bots rather than topping each bot to a target — so the faucet is a number the owner tunes, not an emergent property of bot count × steal rate. Add an anomaly check for players whose `pvp_steal` gold from `is_bot=true` defenders exceeds N/day, and put `bot_gold_outstanding` on the same dashboard so the retirement schedule is visible.

### §14 — the Dockerfile does not build. `COPY --from=build /usr/share/zoneinfo /usr/share/zoneinfo` reads a path that does not exist in `golang:1.27-alpine`.

**Breaks because:** Alpine does not ship timezone data; the official golang alpine images install `ca-certificates` but not `tzdata`, so `/usr/share/zoneinfo` is absent and BuildKit fails the COPY with "failed to compute cache key: /usr/share/zoneinfo: not found". The line is also redundant: `gcr.io/distroless/static` already contains ca-certificates, an /etc/passwd root entry, /tmp, and tzdata (distroless base README) — which is the very reason §14 gives for rejecting `scratch`.

**Fix:** Delete the line. If a named location is ever genuinely needed (nothing in this design should need one — every timestamp is `timestamptz` and every client countdown runs off `X-Server-Time-Ms`), use `import _ "time/tzdata"`, which embeds the database in the binary for ~450 KB, rather than a filesystem COPY. Verify `docker build` succeeds in CI at milestone 1, before any game code exists.

### §5.4 — `app.apply_rates` recomputes `ts` without re-applying the monotonicity clamp `app.settle_player` applies, then writes both anchors from that unclamped value.

**Breaks because:** settle_player deliberately does `ts := GREATEST(ts, r.energy_anchor_at, r.tax_anchor_at)` and calls that guard load-bearing ("a clock that jumps backwards must never rewind an anchor"). apply_rates then does its own `ts := COALESCE(p_now, now())` — raw and unclamped — and writes `tax_anchor_at = ts` and `energy_anchor_at = ts - (rem_ms * new_period / old_period)`. If `p_now` is behind an existing anchor (NTP step on the VPS, two concurrent requests where the second carries an earlier Clock read, or blue/green containers with skewed clocks), both anchors rewind into the past and the next settle re-credits that interval: a free energy and tax grant, triggered by buying a family upgrade or allocating a stat point — the two most-repeated actions on the Family tab.

**Fix:** After `r := app.settle_player(p_id, p_now);`, use `ts := GREATEST(COALESCE(p_now, now()), r.energy_anchor_at, r.tax_anchor_at);` — settle already returned the clamped anchors in `r`, so this is one line reusing them. Add to milestone 3's gate: `TestApplyRatesNeverRewindsAnchor` — settle at t0+60s, call apply_rates with `p_now = t0`, assert both anchors are >= their pre-call values and that a subsequent settle at t0+60s credits zero.

### §0/§3 — the "≤ 3 DB round trips per mutating request" budget, which is the entire quantitative basis for the DigitalOcean-over-Hetzner decision, is contradicted by the design's own code.

**Breaks because:** §6.4 counts a collect as "1 (statement) + 1 (idempotency claim) + 1 (idempotency complete) = 3", omitting BEGIN and COMMIT, which pgx sends as separate round trips — so 5, before the §5.5 `settleAndSync` call the service layer also performs. §8.1's Attack is far worse: BEGIN, idempotency claim, 2× SettlePlayer, CountRecentBattles, 2× snapshotSide (each at least soldiers + items), PvPDebitDefender, PvPCreditAttacker, InsertBattle, 2 ledger inserts, InsertNotification, idempotency complete, COMMIT ≈ 17. At the design's own 15–18 ms Hetzner figure that is ~280 ms per attack, not 50 ms — the decision is directionally right but its magnitude is understated ~5×, and nobody reading the doc will size the pool or the p99 alert correctly.

**Fix:** Restate the budget per endpoint as a measured SLO rather than an assertion: add a `db_round_trips{route}` counter fed by the pgx QueryTracer and set milestone gates on real numbers (collect ≤ 5, attack ≤ 8 after batching). Then actually batch PvP: collapse the two `snapshotSide` calls into one `pgx.Batch` (4 queries, 1 round trip) and the debit/credit/battle-insert/2×ledger/notification tail into a second — taking attack from ~17 to ~7, and making this the one place where the `pgx.Batch` pipelining §0 promises is actually used.

### §17/§8/§10 — `shield_until` is modelled three inconsistent ways, and `newbie_until`'s default defeats the primary anti-alt-farming control.

**Breaks because:** Schema: `shield_until timestamptz NOT NULL DEFAULT '-infinity'`. §8.1 Go: `defender.ShieldUntil.Valid && …` — a nullable pgtype. §10 payload: `"shield_until": null`. §8.1 SQL: `shield_until = COALESCE(@shield_until, shield_until)`, requiring a nullable parameter. With sqlc generating from the NOT NULL schema, `.Valid` will not compile and the COALESCE parameter type is wrong. Separately, `newbie_until timestamptz NOT NULL DEFAULT now()` means any insert path that forgets to override produces a player whose newbie shield expired at creation — and §16 names that shield as the primary defence against the exploit the design itself calls "the exploit most likely to be found first".

**Fix:** Keep NOT NULL + the `'-infinity'` sentinel — it is the right choice, keeping `shield_until <= @now` index-friendly with no NULL handling. Then: drop `.Valid` from the Go guard (`defender.ShieldUntil.After(now)`); serialize `-infinity` as JSON `null` in the same custom marshaller that handles `Amount`, so the client contract stays clean; change the debit query to `shield_until = GREATEST(shield_until, @shield_from::timestamptz)` passing `'-infinity'` for the no-shield case — which also gives you §8.3's stacking semantics for free. Change the newbie default to `DEFAULT now() + interval '24 hours'` so the safe value is the default.

### §18 milestone 12 — Apple StoreKit 2 / App Store Server Notifications V2 is one table row for what is realistically a week of work, and none of its prerequisites are in the design.

**Breaks because:** Verifying a `signedTransaction` means validating the JWS `x5c` chain — leaf, Apple WWDR G6 intermediate, Apple Root CA G3 — against a pinned copy of Apple Root CA G3, which must be embedded. G3 is the ECDSA root and is not usable from the system TLS trust store for this (JWS verification does not consult TLS roots at all), so §14's argument that distroless/static's ca-certificates covers outbound TLS is irrelevant here. Apple publishes App Store Server Library for Java, Python, Node and Swift — not Go — so chain build/validation, certificate-expiry handling (production-wide failures from expired x5c intermediates occurred in Oct 2025), `bundleId`/`environment`/`appAppleId` assertions, sandbox-vs-production routing, `transaction_id` uniqueness, and `REFUND`/`REVOKE`/`CONSUMPTION_REQUEST` handling all have to be written. None appear in the secret inventory (no Apple Root CA G3 asset), the schema (no `iap_transactions`, no product→diamonds catalog), or the API (`/v1/iap/apple/verify` takes a `signed_transaction` and returns `granted_diamonds` with no product mapping).

**Fix:** Budget a full milestone. Add migrations for `iap_products (product_id text PK, diamonds bigint, active bool)` and `iap_transactions (transaction_id text PK, original_transaction_id text, player_id uuid, product_id text, environment text, purchased_at timestamptz, revoked_at timestamptz)`; embed `AppleRootCA-G3.cer` via `embed.FS`; verify with `crypto/x509` `CertPool` + `Certificate.Verify` on the decoded x5c chain, then `golang-jwt/v5` with the leaf's ES256 public key. Grant diamonds in the same transaction as the `iap_transactions` insert with `ON CONFLICT (transaction_id) DO NOTHING` (0 rows = replay → return the prior grant). Handle REFUND/REVOKE with a compensating ledger entry per the design's own "corrections are reversing entries" rule, and decide explicitly whether diamonds may go negative after a refund-post-spend, because that will happen.


## MINOR (3)

### §10 — the JSON number rule fixes precision but not type, and Godot 4.4+ parses *every* JSON number as a float.

**Breaks because:** The design correctly requires values above 2^53 to be strings, then says "Small bounded integers (level, energy_current, energy_max, counts, basis points) stay as JSON numbers." But Godot's JSON parser returns all numbers as float, not only large ones (godotengine/godot#61464, #75821, #103801; the behaviour tightened between 4.3 and 4.4 so arrays of ints now come back as arrays of floats). So `level`, `slot_index`, `window_id`, `reroll`, `unspent_stat_points` and every basis-point value arrive in GDScript as floats: as `Dictionary` keys they silently miss (`d[1.0]` is not `d[1]`), as array indices they need casts, and `match` against integer literals fails. This is a client-contract defect owned by this document, since the document declares the rule.

**Fix:** State it in the contract and give the client a decode layer: every response type gets a hand-written `from_dict()` in GDScript doing explicit `int(d["level"])` / `d["gold"].to_int()` coercion at the boundary, with nothing downstream reading the raw parsed dictionary. Mark each field in `api/openapi.yaml` with a vendor extension (`x-amount: true` for string-encoded, plain integer otherwise) and generate the GDScript decoders from it so the two cannot drift. Worth considering as the cheaper rule: serialize ALL integers as strings and coerce uniformly — one rule instead of two, and it removes the 2^53 judgement call from every future field.

### §17 — kingdom membership has two sources of truth, and the PvP fairness check reads the one that is not canonical.

**Breaks because:** `kingdom_members` has `player_id uuid PRIMARY KEY` (correctly: one kingdom per player) and holds `role` and `reputation_contributed`, while `players.kingdom_id` is a separate FK column. §8.1's same-kingdom guard reads `players.kingdom_id`; roles, invites, kick and the member list read `kingdom_members`. Any path that updates one and not the other — a kick that forgets the player row, a leave racing a kingdom delete's `ON DELETE SET NULL` — lets kingdom-mates attack each other, which the brief forbids outright, and does so silently.

**Fix:** Declare `kingdom_members` canonical and `players.kingdom_id` a denormalization maintained in the same transaction, with a nightly consistency check in the anomaly scan (`SELECT count(*) FROM players p FULL JOIN kingdom_members m USING (player_id) WHERE p.kingdom_id IS DISTINCT FROM m.kingdom_id` → severity 3). Better if you can afford one extra indexed read on the attack path: drop `players.kingdom_id` and read membership from `kingdom_members` in the same batch as the snapshot queries — one source of truth is worth more than one round trip on a path already paying ~17.

### §9.1 — the stated reason for rejecting PCG is not correct. It does not change the (correct) choice of ChaCha8, but the reasoning should not be carried forward as precedent.

**Breaks because:** The argument is that PCG's "state is small enough that a player who observes a handful of outputs can in principle recover it and predict future recruit tiers and shop rolls", and that "Shop windows are publicly predictable in time, so this is a live concern." But every roll is seeded by a *fresh* HMAC-SHA256 output under a server-held key, domain-separated by purpose and keyed on (player_id, window, reroll). Recovering the stream state for window N reveals nothing about the seed for window N+1, because that seed is an HMAC output the attacker cannot compute without the key. The security comes entirely from the keyring, not the PRNG; the only thing a state recovery leaks is the remaining draws of a stream whose full output the player is already shown.

**Fix:** Keep ChaCha8 — it is free, consumes the full 32-byte digest with no truncation, and removes a whole class of "is this predictable?" argument from future review. Correct the rationale in the document to "full 32-byte seed, no truncation of the HMAC digest, and no need to reason about state recovery at all," so nobody later concludes that seed secrecy can be relaxed because the PRNG is strong.


## Missing coverage

- Combat resolution is entirely unspecified. §8 details locking, gold transfer and auditability in depth, but `battle.Resolve(cfg, aSnap, dSnap, seed)` is a black box: how player Attack/Defense stat points combine with soldier base stats and equipped item Attack/Defense, whether soldiers duel 1v1 or fight as an aggregate pool, how damage is derived, how many rounds, and what win probability a given power ratio produces. This is the formula that makes items, rarities, soldier tiers and stat allocation meaningful, and it is exactly what the pure `internal/game` boundary exists to make testable. Milestone 9 cannot be scoped without it.
- The definition of `players.power` is missing, yet it is the matchmaking key. `FindAttackTargets` bands on `power` at 0.80x–1.25x, `players_matchmaking_idx` and `players_lb_power_idx` are built on it, the anomaly detector re-verifies it, and §7.1 says it is recomputed on equip/recruit/dismiss/stat-change — but no formula is given. If power is a poor proxy for battle outcome (e.g. it sums Attack+Defense while combat is multiplicative), the fairness argument in §8.2 collapses and every fight inside the band is a blowout.
- Item drops are a dead concept. `items.source` allows 'drop', `rng.PurposeDrop` and `SEED_KEY_DROP` are defined, but no endpoint, battle outcome or job milestone ever produces one. Either wire it (a drop on PvP win is the obvious hook, and the reason to keep `PurposeDrop` domain-separated) or delete the enum value, the purpose and the secret — a half-wired faucet is exactly what gets completed later without an economy review.
- Inventory capacity is asserted but not implemented. `/v1/state` returns `inventory_summary: {count: 47, capacity: 200}` with no `capacity` column, no source in the config bundle, no enforcement in shop buy or recruit, and no defined behaviour when full (reject the purchase? auto-sell? drop the drop?). For a game whose only item sink is manual selling, an unenforced cap means unbounded `items` growth per whale plus an `/v1/inventory` cursor query with no supporting index on (player_id, id).
- The seven-tier rarity ladder has no stat-multiplier table, and the epic/mystic colour conflict the brief explicitly flagged gets no resolution proposal. §12 correctly moves colours into the config bundle so it is fixable without a client release, but the brief asked for a proposal. Concretely needed: `rarities[].stat_mult_bp` for all seven tiers, the shop and per-soldier-type rarity weight tables (which the validator already requires to sum to 10000, but which are never given), and a colour proposal — e.g. mystic to #EC4899 magenta or #06B6D4 cyan, keeping epic at #8B5CF6, since red is already taken by special.
- Diamond sinks other than shop reroll are absent from the API. The brief names energy refills, protection purchase, shop rerolls and premium packs; only `/v1/shop/reroll` exists. Beyond the missing revenue, this has a technical consequence the design missed: a purchased energy refill is a second source of energy, which breaks the §7.5 faucet-ceiling formula (it assumes regeneration is the only input) and would flag every paying player as a severity-4 exploit. The ceiling must add a `refills_granted_in_window * refill_amount` term sourced from the ledger.
- APNs push is named as the correct answer for 'you were attacked while offline' but is never scheduled, and there is no `device_tokens` table, no APNs key in the secret inventory (only APPLE_P8 for StoreKit), and no notification-preference storage. In an asynchronous PvP game where the only feedback for being attacked arrives at next app open, this is the primary retention mechanic, not a nice-to-have.
- Account deletion and data export are missing. `deleted_at` and 'retained 30 days for support' appear in the link-conflict flow, but there is no purge job, no `/v1/player/delete`, and no export endpoint. Apple App Review Guideline 5.1.1(v) requires in-app account deletion for any app supporting account creation, so this blocks the first submission — and the ledger's append-only design means the erasure strategy (pseudonymize player_id vs. delete rows) has to be decided before launch, not after.
- There is no cost model. The design makes two decisions with direct billing consequences — disabling Neon scale-to-zero on production (its own risk list flags this but never quantifies it) and a $24/mo DO droplet — plus Grafana Cloud, Sentry, R2 and GHCR. Neon confirms scale-to-zero is a paid-plan toggle and that disabling it means an always-active compute; the owner should see the monthly figure before the first invoice, weighed against simply accepting the few-hundred-ms cold start during the low-traffic hours of a launch-scale game.
- Backpressure during a Neon resume is unhandled. `connect_timeout=10` plus a role-level `statement_timeout=8s` sits under a 10-second HTTP middleware timeout, so a compute resume landing mid-request can consume the entire budget and surface as a bare 500. There is no load shedding, no circuit breaker, and no explicit 503 + Retry-After path for 'database is resuming' — the single most likely early-launch incident given the design's own risk list flags cold starts.
- The Collect job ladder has no progression. The brief's example ladder is 1 energy -> 2 gold, 2 -> 4: a flat 2 gold per energy at every rung, so unlocking a higher job buys nothing but fewer taps for the same income — and the per-job milestone counters (25/50/100) actively punish switching, making 'never advance' optimal. The design should have flagged this. `internal/game/economy` needs an explicitly increasing gold-per-energy curve, with `cmd/simulate` charting gold/hour by unlocked tier as a publish-preview output.
- The `settleAndSync` fast path and the self-settling action statements overlap and are never reconciled. §5.5 has the service call `SettlePlayer` at the top of every request; §6.4's action statement calls `app.settle_player` again itself. The second is a no-op only because settle is idempotent — but it is an extra round trip on every action, it is why the '3 round trips' count is wrong, and once §6.4 becomes a plpgsql function the ownership question must be answered explicitly: either the service settles and the action does not, or the reverse. Write the rule down, because the design's own risk list names 'someone adds a path that mutates players without settling' as the most likely long-term source of a subtle economy bug.

## The corrected collect (replaces §6.4 wholesale)

This is the change that matters most, because §6.4 is declared "the template every other mutating action copies."

**The rule to write into the repo and enforce in CI:** *`app.settle_player` must never be called from a SQL statement that also writes `players`.* A single SQL statement — including all of its CTEs and any volatile function it calls — executes under one snapshot with one output command id. settle's `UPDATE` is invisible to the outer `UPDATE`, and the outer `UPDATE`'s `heap_update` then hits the already-modified tuple. Inside plpgsql this problem does not exist, because plpgsql runs a `CommandCounterIncrement` between statements.

```sql
CREATE OR REPLACE FUNCTION app.collect(
    p_id uuid, p_now timestamptz, p_job_id text, p_times int,
    p_energy_cost int, p_required_level int,
    p_base_gold bigint, p_base_xp bigint,
    p_gold_mult_bp int, p_xp_mult_bp int,
    p_ms_at int[], p_ms_bp int[],
    p_level_xp bigint[], p_points_per_level int,
    p_idem_key text, p_config_ver int
) RETURNS app.collect_result       -- composite: players columns + gold_gain, xp_gain, collects, old_level
LANGUAGE plpgsql AS $$
DECLARE
    r players; new_collects bigint; g_gold bigint; g_xp bigint;
    new_level int; old_level int;
BEGIN
    -- 1. settle + lock. Its own SQL command; everything below sees its writes.
    r := app.settle_player(p_id, p_now);
    old_level := r.level;

    IF r.energy_current < p_energy_cost * p_times THEN
        RAISE EXCEPTION 'insufficient_energy'
            USING ERRCODE = 'P0001',
                  DETAIL  = format('%s/%s', r.energy_current, p_energy_cost * p_times);
    END IF;
    IF r.level < p_required_level THEN
        RAISE EXCEPTION 'level_locked' USING ERRCODE = 'P0001';
    END IF;

    -- 2. counter bump
    INSERT INTO player_job_stats AS pjs (player_id, job_id, collects)
    VALUES (p_id, p_job_id, p_times)
    ON CONFLICT (player_id, job_id) DO UPDATE SET collects = pjs.collects + p_times
    RETURNING pjs.collects INTO new_collects;

    -- 3. reward: pure arithmetic, milestone applied per collect within the batch
    SELECT COALESCE(SUM(
             ( p_base_gold
               * (10000 + COALESCE((SELECT MAX(m.bp)
                                      FROM unnest(p_ms_at, p_ms_bp) AS m(at, bp)
                                     WHERE new_collects - p_times + g.i >= m.at), 0))
               / 10000
             ) * p_gold_mult_bp / 10000
           ), 0)
      INTO g_gold
      FROM generate_series(1, p_times) AS g(i);

    g_xp := p_base_xp * p_times * p_xp_mult_bp / 10000;
    SELECT count(*) INTO new_level FROM unnest(p_level_xp) t WHERE t <= r.xp + g_xp;

    -- 4. the balance write. Sees the settled tuple. No self-update conflict.
    UPDATE players p SET
        energy_current      = p.energy_current - p_energy_cost * p_times,
        gold                = p.gold + g_gold,
        xp                  = p.xp   + g_xp,
        lifetime_gold       = p.lifetime_gold + g_gold,
        level               = new_level,
        unspent_stat_points = p.unspent_stat_points
                              + (new_level - old_level) * p_points_per_level,
        updated_at          = p_now
      WHERE p.id = p_id
    RETURNING p.* INTO r;

    -- 5. journal, same transaction
    INSERT INTO ledger (player_id, currency, delta, balance_after, reason,
                        ref_type, ref_id, idem_key, config_ver, created_at)
    VALUES (p_id, 'gold', g_gold, r.gold, 'collect', 'job', NULL, p_idem_key, p_config_ver, p_now),
           (p_id, 'xp',   g_xp,   r.xp,   'collect', 'job', NULL, p_idem_key, p_config_ver, p_now);

    RETURN (r, g_gold, g_xp, new_collects, old_level)::app.collect_result;
END; $$;
```

Notes on this shape:

- **Still one network round trip.** The whole point of §6.4 survives.
- **`RAISE EXCEPTION` is compatible with §6.2.** The savepoint the idempotency wrapper already takes absorbs it, so the business error is committed alongside the idempotency row exactly as designed. Map `P0001` + message to the taxonomy in `httpx/problem.go`.
- **The `guard`-CTE subtlety disappears.** The old version relied on `INSERT … SELECT FROM guard` returning zero rows to suppress the counter bump. That reasoning was correct, but note the adjacent landmine it papered over: the old `award` CTE, being an ungrouped aggregate, returns one row with a *non-zero* `xp` even when `bump` is empty — only the `FROM guard g` in `upd` prevented granting it.
- **If you keep any multi-CTE statement that reads `settled`, mark it `AS MATERIALIZED`.** PostgreSQL will not inline a CTE containing a volatile function today, but making it explicit removes the possibility that a refactor turns one settle into two.
- **CI guard, extended from the design's own risk list:** `grep -l 'settle_player' db/queries/*.sql | xargs grep -l 'UPDATE players'` must return nothing.

Apply the same treatment to `tax/claim`, `shop/buy`, `soldiers/recruit`, `family/upgrades/{key}/buy`, `player/stats/allocate`. `apply_rates` is already correct in this respect (it calls settle then updates as two plpgsql statements) — only its `ts` clamp needs the one-line fix.
